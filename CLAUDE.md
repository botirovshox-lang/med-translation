# CLAUDE.md — Medical CAT Translator (корень репозитория)

Правила для AI-ассистентов и разработчиков. Прочти перед любыми изменениями.

## Что здесь актуально

- **`backend/main.py`** — весь продакшен-бэкенд (FastAPI, ~25 эндпоинтов). Одним файлом, это осознанно.
- **`backend/medical_qa.py`** — медицинский QA (структурные/числовые проверки, обратный перевод).
- **`frontend/`** — React 18 **без сборки**: UMD + Babel standalone, `.jsx` компилируются в браузере.
- **`deploy/medcat.service`** — источник истины для systemd-юнита (копируется в `/etc/systemd/system/`).
- **`tools/after_run.py`** — отчёт после прогона: счётчики задачи, корзины разбора,
  состав следующего прогона и сравнение с прошлым снимком. Вызовов модели нет,
  код возврата 1 = «есть на что посмотреть» (годится для cron).
- **`med_translation/`** — legacy Streamlit-код; из него используются только модули
  (глоссарий TSV в `assets/glossary/`, `medical_qa`, `tm`, `db`, `pipeline`) через `sys.path` в `main.py`.
- **`med_translation/CLAUDE.md`** — правила отдельного legacy-подпроекта (TM-билдер из PDF), не про этот бэкенд.

## Жёсткие инварианты (нарушение = потеря данных)

1. **Ровно 1 uvicorn worker.** `STATE` — глобальный dict в памяти процесса,
   `state.json` — его снапшот. Два воркера затирают данные друг друга.
2. **Все мутации `STATE` заканчиваются `save_state(STATE)`.** Запись атомарна
   (tmp + `os.replace` под `_SAVE_LOCK`) — не заменяй на прямую запись.
3. **Писать на диск можно только в `backend/data/`** (systemd `ProtectSystem=full`,
   `ReadWritePaths`). Экспорты — в `data/exports/`, бэкапы — в `data/backups/`.
4. **Никаких демо-заглушек в target.** Ошибка перевода → HTTP 502 / `{"ok": false, "error": ...}`,
   сегмент не трогать. То же на фронтенде: не подставлять фейковый текст при недоступном сервере.
5. **Изменил `frontend/js/*` → бампни `?v=` во всех строках `frontend/index.html`.**
   Иначе пользователи получат старый кэш и «загадочные» баги.
6. **Модели и цены живут только в `OPENAI_MODELS`.** Фронтенд берёт их через
   `/api/models`; хардкод id или цены в `.jsx` — ошибка. Единственное исключение —
   `AUX_MODEL_PRICES`: модели, которые человек не выбирает (эмбеддинги), но
   которые стоят денег. В `OPENAI_MODELS` им не место, из него строится
   выпадающий список — а без цены их расход считался бы нулём.
7. **Платные прогоны (перевод, back-check, судья) не запускай ради проверки.**
   Логику отбора проверяй запросами, которые заведомо попадают в кэш.
8. **Автоматически глоссарий пополняется только уровнем `auto`.** Находки идут
   в `STATE["termQueue"]` и ждут решения. Автоодобрение (`/api/term-queue/auto-approve`)
   раскладывает однозначных кандидатов само, но пишет их подсказкой (`tier: auto`),
   которую модель вправе игнорировать. Приказом (`tier: verified`) запись становится
   от человека (кнопка одобрения в очереди), от трёх независимых чистых сегментов
   либо от **внешнего справочника** (`backend/authority_data/`, см. `authorities.py`).
   В медицине, фарме и юриспруденции (`AUTO_APPROVE_BY_DOMAIN`) согласия сегментов
   для приказа НЕ хватает — там приказ даёт только человек или **выверенный**
   справочник (`# tier: verified`).
   **Снять этот запрет можно только явным разрешением человека на КОНКРЕТНЫЙ
   запуск** (`allow_verified` у `/auto-approve`, тумблер «Приказ по согласию
   сегментов»). Отдельным полем, а не правкой `AUTO_APPROVE_BY_DOMAIN`, именно
   потому, что это разовое разрешение, а не новая политика: оно видно в ответе
   (`policy.humanOverride`), на записи глоссария (`byOverride`, примечание) и
   в истории пачек (`override`), и откатывается вместе с пачкой. Снимается
   ровно запрет — порог сегментов, требование РАЗНЫХ исходников,
   единственность варианта и вето корпуса остаются. Молчаливого ослабления
   защиты быть не должно: без этих пометок через месяц не ответить, откуда
   в медицинском глоссарии машинные приказы.
   **Выверенный справочник обходит запрет области намеренно и законно**: запрет
   касается САМОодобрения (система заверяет собственный перевод), а справочник —
   источник вне контура. **Краудсорсный (`# tier: auto`) запрет НЕ обходит**:
   он лишь снижает порог согласия сегментов на один (не ниже двух) и только там,
   где самоодобрение вообще разрешено. Тумблер «только подсказки» (`max_tier`,
   ключ `cap_soft`) сильнее любого справочника: это просьба человека на запуск.
   Подтверждение сегмента-донора приказа НЕ даёт: человек заверил перевод строки,
   а не правило для всех будущих текстов. Правило «приказ
   даёт человек» и есть защита от закрепления собственных ошибок перевода;
   ослаблять её ради удобства нельзя.
9. **Правки TM и глоссария не переписывают чужой текст молча.** Подтверждение возвращает
   список повторов, распространение — отдельная команда `/propagate`, подтверждённые
   сегменты по умолчанию не трогаются (так же ведут себя Phrase и Trados).
10. **Все `/api/*` требуют токен сессии** (`Authorization: Bearer`), проверка — в мидлвари
   `require_token`. Публичны только `PUBLIC_API_PATHS` (login, logout, health);
   расширять этот список — значит открыть эндпоинт всему интернету.

## Деплой (VPS 31.129.100.106, домен trasnlateuz.duckdns.org)

```bash
cd /opt/med-translation && git pull && git log -1 --oneline   # НЕ прячь пул за | tail: код возврата пропадёт
systemctl restart medcat
# поднимается ~15 с (state.json + глоссарий) — сразу после рестарта curl получит refused
for i in $(seq 1 15); do sleep 2; curl -s --max-time 5 http://127.0.0.1:8000/api/health && break; done
```
Секреты в `/etc/medcat/env` (не в git): `APP_PASSWORD`, `OPENAI_API_KEY`.
`GOOGLE_TRANSLATE_API_KEY` больше не используется — Google убран из системы.
**`APP_PASSWORD` обязателен** — дефолта в коде больше нет. Если переменная пуста, сервис
стартует со случайным паролем и пишет его в journal (`journalctl -u medcat | grep APP_PASSWORD`),
то есть все пользователи окажутся заперты снаружи. Необязательные: `ALLOWED_ORIGINS`
(CORS-белый список, через запятую), `SESSION_TTL_HOURS` (по умолчанию 12).

Репозиторий принадлежит `medcat`, деплой идёт от root: `/opt/med-translation` прописан
в `safe.directory` root'а, часть объектов `.git` root-овая — пул от `medcat` уже не пройдёт.

## Известные особенности

- **Google Translate убран.** Переводит ТОЛЬКО выбранная модель: бесплатный движок
  не знал предметной области, игнорировал глоссарий и давал текст, который всё равно
  чинили платными прогонами. Нет ключа OpenAI — нет перевода: 503 с внятной причиной,
  не заглушка и не «черновик бесплатным движком». Ключ требуется, только если хоть
  один сегмент придётся переводить: порция из одних совпадений с памятью работает
  без него. `provider: "google"` и `route: "GOOGLE_SAFE"` остаются в исторических
  сегментах — это факт о том, чем их перевели; новые так не помечаются.
- **Отбора по `risk` при переводе больше нет.** Он делил сегменты между Google
  и моделью, и запуск «не той» кнопки молча оставлял половину проекта
  непереведённой. `risk` — по-прежнему длина сегмента, но на движок не влияет.
- **Соседние сегменты уходят в промпт перевода** (`_neighbours`,
  `NEIGHBOUR_CHARS`). До этого сегмент переводился в полном одиночестве, и
  обрывки списка («Выделяют:», «плевры,», «формирование каверн и распространение
  процесса.») попадали в модель без всякого признака того, к чему относятся.
  Соседи даны как ОБСТАНОВКА, и запрет переводить их сказан дважды: модель
  добросовестно переписывает всё, что ей дали, — на импорте это уже случалось
  с соседними абзацами.
  **В обратный перевод (`literal=True`) соседи не идут НИКОГДА.** Back-check
  стоит на том, что обратный перевод ОТРАЖАЕТ текст, а не понимает его: дай
  ему обстановку — он починит кривой английский по смыслу соседей и спрячет
  ровно ту ошибку, которую проверка ищет.
  У группы одинаковых исходников соседи берутся у ПЕРВОГО сегмента: перевод
  у группы один на всех (дедупликация повторов), и выбрать «правильных» соседей
  для заголовка, стоящего в трёх местах документа, нельзя в принципе.
  Цена посчитана на боевом проекте: вход 1534 тыс. → 1931 тыс. токенов (+26%),
  выход не меняется. Готовые переводы это не трогает — только новые.
- **Контекстный арбитр спорного термина (`POST /api/projects/{pid}/term-context`).**
  Единственный вызов, которому дают соседей ВМЕСТЕ с вопросом: «правильно ли
  передан термин ИМЕННО ЗДЕСЬ». Нужен потому, что остальные проверки смотрят
  на сегмент в одиночку, а термин живёт в ряду: «туберкулёз лёгких» обратный
  перевод возвращает как «лёгочный туберкулёз» — по словам потеря, по смыслу
  то же самое. Спрашивается только про ПРИКАЗНЫЕ записи, вокруг которых спор
  (`_term_disputes_of`): не пережил обратный перевод либо забракован termcheck.
  Один вызов на сегмент, сколько бы спорных терминов в нём ни было.
  Вердикт лежит НА СЕГМЕНТЕ (`seg["termContext"]`) и устаревает вместе с
  текстом и версией вопросов (`TERM_CONTEXT_VERSION`) — как back-check,
  termcheck и сверка смысла. Меняешь промпт — поднимай версию.
  **«Передан верно» СНИМАЕТ претензию** (`_repair_findings` пропускает такой
  `term_lost` по запомненной форме): арбитр единственный видел сегмент в ряду,
  и оставить претензию значит послать ремонт переписывать верный перевод.
  **«Передан неверно» ремонту НЕ отдаётся, и это не забывчивость.** Арбитр
  предлагает вариант, отличный от утверждённого перевода, а `_repair_scores`
  считает нарушенные приказные термины всегда: подставь совет — счётчик
  вырастет, правка откатится. Заход с заранее известным исходом, ровно та
  оплачиваемая карусель, от которой заведён `_repair_futile`. Вопрос здесь
  про ЗАПИСЬ глоссария, а не про строку, поэтому вердикт уходит человеку
  в `/analysis` (`human.termContextWrong`) с доводом и готовым вариантом:
  исправит запись — и все затронутые сегменты приведёт в порядок существующий
  расчёт соответствия.
  **Совет проверяется БЕСПЛАТНО перед показом**: предложенный вариант
  спрашивается у корпуса целевого языка (`_corpus_check`). Ноль вхождений —
  калька, вариант снимается с объяснением; молчание корпуса («не знаю»)
  не одобряет и не блокирует — тот же закон, что у `attested()` везде.
- **Промпт перевода собирает `_translate_system`** — отдельно от вызова модели,
  чтобы его можно было проверить тестом: от того, уходит ли запись глоссария
  приказом или подсказкой, зависит, повторит ли модель чужую ошибку.
- **Регистр букв портит ГЛОССАРИЙ, а не модель** (`_case_misses`, правило 8
  в `_translate_system` и в `_repair_system`). «use these exact translations»
  модель понимает буквально и копирует НАЧЕРТАНИЕ записи вместе со словом,
  поэтому приказ «Туберкулема → Tuberculoma» ставил заглавную посреди фразы,
  «ТУБЕРКУЛЕЗ ОРГАНОВ ДЫХАНИЯ → RESPIRATORY TUBERCULOSIS» — капс посреди фразы,
  а «Фиброзно-кавернозный туберкулёз → fibrocavitary tuberculosis» роняло
  строчную в начало заголовка. На боевом учебнике так вышло у 36 сегментов
  из 2711. Правкой записей это не чинится: у записи один регистр, а мест,
  куда она встаёт, много, — поэтому промпт говорит прямо, что начертание
  записи в требование НЕ входит и ставится по месту в предложении.
  **Промпт лечит только НОВЫЕ переводы**, а уже написанный текст без находки
  никто не пересмотрит — отсюда `_case_misses`: бесплатная детерминированная
  претензия рядом с `_gloss_misses`, тем же путём попадающая в ремонт
  (`_repair_findings`), в его оценку (`_repair_scores["case"]`, сверяется
  ВСЕГДА — как глоссарий) и в состав прогона (`_plan_step`).
  Правил ровно три, и все проверены на боевых данных (38 находок на 2711
  сегментах, ни одной ложной): строчная в начале там, где в оригинале
  заглавная; потерянный КАПС заголовка (от `CASE_CAPS_MIN` букв — «МБТ»
  и «ВИЧ» заголовками не считаются); капс-ЦЕПОЧКА из двух и более слов,
  которой в оригинале не было (одиночное слово капсом — законная
  аббревиатура «ELISA», и находкой не считается). Обратного правила
  «в оригинале строчная, в переводе заглавная» нет намеренно: английский
  законно поднимает регистр там, где русский его не поднимает (народы,
  месяцы, дни недели), и такое правило кричало бы на верный перевод.
  Письмо без регистра (иероглифы, арабица) — молчим: тот же закон, что
  у `DOMAIN_RULES`.
  **Сравнение «модель ничего не изменила» идёт по `_same_words`, а не по
  `_norm_key`**: тот приводит текст к нижнему регистру, и правка, у которой
  всё отличие в заглавной букве, читалась бы как «нечего менять» — сегмент
  получал бы клеймо `tried` и не чинился бы больше НИКОГДА.
  `_machine_clean` регистр не смотрит намеренно: пара «оригинал → перевод»
  от начертания не портится, а сверка глоссария и так регистронезависима.
- **Начертание глоссарного термина берётся у ОРИГИНАЛА, 1в1** (`_case_like`,
  `_term_case_misses`). Запись хранит ОДНО начертание, а мест, куда она встаёт,
  много: «Туберкулема» стоит и заголовком, и посреди фразы. Правильный ответ
  даёт не запись, а сам оригинал — как термин написан в ЭТОМ сегменте, так он
  пишется и в переводе. Форма из текста у нас есть (`_form` из `_get_context`),
  поэтому подгонка **детерминированная**, а не просьба к модели: в промпт
  уходит `форма из сегмента → перевод в её начертании`, и словарного варианта
  модель не видит вовсе — копировать нечего. Так же собирается список
  утверждённых терминов в промпте ремонта.
  Три направления и у каждого оговорка:
  1) **оригинал КАПСОМ → перевод капсом**, но только от `CASE_CAPS_MIN` букв.
     Короче — это АББРЕВИАТУРА, и она не говорит о начертании ВООБЩЕ:
     «ПТП» стоит капсом и посреди фразы, а расшифровка «anti-tuberculosis
     drugs» — обычное словосочетание, и поднять ей регистр значило бы
     испортить перевод (на боевых данных — 17 сегментов). Начертание
     неизвестно — не трогаем ничего;
  2) **оригинал с заглавной → заглавная**: поднять регистр безопасно всегда;
  3) **оригинал со строчной → строчная, КРОМЕ имён и аббревиатур** — это
     единственное опасное направление. «реакция Манту → Mantoux reaction»,
     «очаг Гона → Ghon focus», «вакцина БЦЖ → BCG vaccine»: опустив первую
     букву, мы испортили бы имя. Признак берётся из САМОЙ записи
     (`_name_bearing`: заглавная не у первого слова оригинала) и из слова
     перевода (`_acronymish`). Аббревиатурой считается КОРОТКОЕ слово капсом
     (`CASE_ACRONYM_MAX`): «RESPIRATORY» — не аббревиатура, а крик из записи.
  **Крик записи снимается ЦЕЛИКОМ, а не с первой буквы**: «ТУБЕРКУЛЕЗ ОРГАНОВ
  ДЫХАНИЯ → RESPIRATORY TUBERCULOSIS» посреди фразы обязано стать «respiratory
  tuberculosis», а не «rESPIRATORY TUBERCULOSIS». Аббревиатуру внутри крика
  выдаёт только СТРУКТУРА (`_shout_keep`: цифра или дефис — «MDR-TB», «2HRE»):
  заглавные там у всех, и правило «короткое слово капсом = аббревиатура»
  превращало «GENERALIZED FORMS OF TUBERCULOSIS» в «generalized FORMS OF
  tuberculosis». Остаточный риск назван честно: аббревиатура без цифры и дефиса
  внутри кричащей записи («BCG VACCINATION») будет опущена — чинится правкой
  самой записи.
  **Проверка смотрит только БУКВАЛЬНЫЕ вхождения** перевода термина: нет
  вхождения вовсе — это забота `_gloss_misses`, и говорить об одном и том же
  дважды нельзя. Заглавная в НАЧАЛЕ ПРЕДЛОЖЕНИЯ законна при любом оригинале
  (`_sentence_start`).
  **Термин ВНУТРИ другого термина своего начертания не диктует**: «ревакцинация
  → revaccination» сидит внутри «Ревакцинация БЦЖ → BCG revaccination», и без
  этого правила две записи правили одно место по очереди, каждая ломая работу
  другой. Проверка и правка считают места ОДНИМ расчётом (`_term_case_spans`):
  разойдись они — отчёт показывал бы одно, а команда делала другое.
  **Форма из оригинала берётся СОГЛАСОВАННАЯ** (`_agreed_form`): требование
  у нас одно на сегмент, а термин может стоять в нём и заголовком, и посреди
  фразы («Туберкулема плотна. …части туберкулемы…»). Разнобой — значит «не
  знаем», и мы молчим: навязать одно начертание всем вхождениям означало бы
  испортить то из них, которое и так верно.
  **Чинится это БЕЗ вызова модели** (`_term_case_fix`, `POST /api/projects/{pid}/term-case`,
  `dry_run` по умолчанию; на экране «Анализ» — строка и кнопка в карточке
  «Соответствие глоссарию»: строка ОСТАЁТСЯ и при нуле, кнопка при нуле
  уходит, а перед правкой показывается, что именно изменится, и сколько
  заверенных человеком не тронуто. Ответ возвращает `ids`, и браузер тянет
  ТОЛЬКО правленые сегменты: проект на 2670 строк весит 5 МБ) — вторая такая команда в системе после
  `/glossary/revert-repairs` и по той же причине: она ничего не сочиняет,
  меняются только заглавные и строчные, слова и их порядок те же. В находки
  ремонта начертание поэтому НЕ идёт: модель на такую претензию переписывает
  предложение целиком, оценка находит, что стало на балл хуже, и откатывает
  правку — на боевом учебнике так застряли 5 сегментов из 77, каждый ценой
  платного вызова. В `_repair_scores` оно при этом остаётся: ремонт, СЛОМАВШИЙ
  начертание, обязан откатиться.
  **Считается это по глоссарию, а `_repair_findings(seg, None)` зовут БЕЗ него**
  (разбор состава и `/analysis` — ради скорости). Поэтому список таких сегментов
  отдаёт `glossary_impact` (`caseSegments`) — тем же проходом и по тем же
  `hits`, второй вызов `_verified_hits` удвоил бы полминуты работы
  единственного воркера. Отдельным списком, а не вперемешку с `segments`: там
  «термина в переводе нет вовсе», здесь «есть, но не в том начертании», и
  смешай их — карточка соответствия звала бы переводить заново то, где надо
  поправить одну букву, а состав прогона отдал бы это ремонту.
- **Буквы чужого письма в переводе ловит `_script_misses`.** Требование
  «Output must be 100% EN» стоит в промпте с самого начала, но оно про ТЕКСТ,
  а рвётся на кусках, которые текстом не выглядят: в готовом переводе учебника
  остались «(МБТ+)», «Р02»/«РС02», «38°С», «2HSЕ/10HE», «2-х», «3х» — кириллица
  внутри формул, единиц и аббревиатур. Глазами это не находится: «РС02»
  и «PCO2» на экране неотличимы, а поиск по документу считает их разными
  строками. Третья бесплатная находка рядом с `_gloss_misses` и `_case_misses`,
  тем же путём в ремонт и в `_repair_scores["script"]`.
  **Письменность считается ПО ТЕКСТАМ, а не по таблице «RU→EN»** (`_script_of`
  по имени символа в Юникоде, `_dominant_script` — по большинству букв):
  хардкодить пару языков нельзя, а «любая встреченная буква» не годится —
  латиница законно стоит в русском оригинале («Mycobacterium bovis»).
  Совпали письменности оригинала и перевода (RU→UK, EN→DE) — МОЛЧИМ: буквы
  там общие, и претензия была бы выдумана. Куски называются поимённо: без
  списка это претензия, которую нечем исполнить.
  **Слепое пятно названо честно**: у сегмента, чей ОРИГИНАЛ набран не своим
  письмом, спрашивать нечего. Так вышло с «2) 2HSЕ/10HE» — шифр схемы лечения,
  где большинство букв латинские, а кириллическая «Е» стоит в самом оригинале
  и переводом добросовестно скопирована. Определять письменность по проекту,
  а не по сегменту, нельзя: `_repair_findings(seg, None)` зовут и разбор
  состава, и `/analysis` — БЕЗ проекта, ради скорости, и правило разошлось бы
  с тем, что делает прогон. Такие сегменты правит человек.
  **Заход ремонта ТОЛЬКО по бесплатным находкам** (регистр и/или письмо)
  меряется их суммой и обязан её УМЕНЬШИТЬ (`only_free`) — ровно как
  `only_minor`: балл не пересчитывался, termcheck не звали, глоссарию
  нарушать нечего, и «не стало хуже» засчитало бы успехом любой переписанный
  текст. Сумма, а не два отдельных счёта: размен регистра на кириллицу —
  не работа.
- **Полоса идущего прогона живёт в залипающей панели** (`RunStrip` внутри
  `.editor-toolbar`), а не в потоке страницы: таблица длинная, прогон идёт
  минутами, и уехавшая за верхний край полоса — это работа, которую не видно
  и нечем остановить. Отдельным `position: sticky` её делать нельзя: два
  залипающих соседа с `top: 0` наезжают друг на друга, а высота панели
  фильтров переменная.
  **Про шаги полоса говорит только то, что знает.** Галочка означает ровно
  «шаг взял всё, что ему отвёл разбор», и ничего больше: подсветить один
  «текущий» шаг нельзя — порция (5 сегментов) проходит ВСЕ выбранные шаги
  по очереди, поэтому незакрытые шаги идут одновременно, на разных порциях.
  «Сделано» берётся из `job.counters[шаг]` (сервер накапливает их в
  `_job_chunk_full`), «осталось» — из снимка состава, который делается при
  запуске (`RUN_SNAP_LS_KEY` в localStorage: прогон переживает вкладку, цифра
  тоже должна). Снимок опознаётся по ТРОЙКЕ «номер + проект + время создания»
  (`runStepRows`): номера задач живут в памяти процесса и после рестарта сервиса
  начинаются с единицы заново, поэтому по одному номеру чужой снимок садился бы
  на неродной прогон — и полоса показывала бы выдуманный остаток вместо честного
  «не знаю». Снимка нет — прогон запущен из другого браузера, и остаток
  НЕ ПОКАЗЫВАЕТСЯ: придуманное число — то самое враньё, ради которого состав
  вообще считает сервер. Разбор во время прогона не пересчитывается (воркер
  на сервере один), поэтому другого источника у «осталось» нет.
  Прогресс-бары в самих карточках убраны: два счётчика об одном и том же
  расходятся, а карточка ещё и уезжает со страницей.
- **Блоки запуска стоят рядом, а не во всю ширину** (`.run-decks`: три колонки —
  составной прогон, одобрение терминов, соответствие глоссарию; две ниже
  1520 px, одна ниже 1180 px). Растянутые на монитор, они читались строчками
  по две тысячи пикселей, и до второй кнопки приходилось листать. Состав
  и причины в строках шагов при этом не урезаны — сокращён только тот текст,
  который целиком повторяется в подсказке у названия. Соответствие глоссарию
  стоит РЯДОМ с одобрением, а не под ним: смотрят на него сразу после
  одобрения, а из-под него оно уезжало под сгиб.
- **Переход к сегменту по номеру показывает ЗОНУ, а не страницу**
  (`zone`, `ZONE_HALF`, строка над колонкой «#» в `.table-head`). Страница
  на десять строк на вопрос «что стоит до и после» не отвечает: сегмент
  оказывается то первой строкой, то последней. Зона — окно по `ZONE_HALF`
  сегментов в каждую сторону, и на время её показа страницы отключены
  (резать 21 строку по десять — снова прятать половину соседей).
  Три правила:
  1) **центр ищется ПО НОМЕРУ на каждом рендере**, а не запоминается индексом:
     сегменты приезжают с сервера заново после каждого прогона, и запомненный
     индекс однажды указал бы на чужую строку; номера нет в проекте — зоны нет;
  2) **переход снимает всё, что сузило список** (статус, риск, поиск, выборку
     из «Анализа») — под фильтром соседей не видно, а зона именно про них —
     и **называет снятое** в уведомлении: молча убранный фильтр человек потом
     ищет глазами по всей панели. Пока зона открыта, об этом сказано полосой
     над таблицей: в ней не весь файл;
  3) на сбросы (`setPage(1)`, `setSelId(null)`) подвешены те же фильтры,
     поэтому переход взводит `jumpRef` — флажок на ОДИН коммит, который гасит
     эффект без списка зависимостей, объявленный ПОСЛЕ сбросов. Без него
     переход, снявший фильтр, тут же улетал бы на первую страницу.
  **Поиск по сегментам живёт ТАМ ЖЕ и он единственный.** В залипающей панели
  его больше нет: два поля на одно состояние — это два места, где его ищут,
  и лишняя высота у панели, из-за которой таблицу видно хуже. Панель от
  таблицы отделяют блоки запуска высотой в экран, так что искать удобнее
  рядом с тем, что ищешь.
- **Один экран прогонов вместо двух.** Шаги конвейера, их модели, состав, цена
  и запуск по отдельности живут в ОДНОЙ таблице (`fullRunRows` + `StepRow`).
  Свёрнутого блока «Отдельные прогоны» больше нет: скрытый в нём переключатель
  менял то, что делает главная кнопка, и человек шёл его искать, чтобы
  не переплатить. У строки два состава и путать их нельзя: `planEst` — что
  сделает ОБЩИЙ прогон (считает сервер, галочки групп на это не влияют),
  `soloEst` — что сделает «Запустить только этот шаг» (считается в браузере
  ПО ГАЛОЧКАМ и идёт со `skip_cached=false`, то есть умеет намеренно
  перепроверить то, что общий прогон считает сделанным). По умолчанию оба
  состава ОБЯЗАНЫ совпадать: `tcGroupDefault` выставляет галочки по тому же
  правилу рангов, что и `_rank_not_weaker` на сервере, а у back-check
  (`BC_DEFAULT_GROUPS`) шкалы нет — там годится свежая проверка любой моделью,
  кроме модели-автора перевода (группа `self`, зеркалит `_backcheck_cached`).
  Разойдись они — под соседними кнопками стояли бы противоречащие числа.
  **У ремонта это равенство держится на списке ДЕЙСТВУЮЩИХ находок, и список
  живёт на сервере** (`TERMCHECK_ACTIONABLE`, отдаётся через `/api/models` —
  как `judgeZone` и `backcheckBands`). Литерал `("critical","major")` в `.jsx`
  — ровно то расхождение, которое случилось, когда ремонту разрешили `minor`:
  строка «Ремонт» обещала 168 сегментов, а кнопка под ней говорила «нечего
  запускать», карточка «Ждут ремонта» показывала своё третье число, а в самом
  сегменте кнопка «Починить» стояла погашенной. Три копии одного правила
  в трёх файлах — три разных ответа.
  Это и проверяет `tests/test_editor_render.js`: фронтенд собирается в браузере,
  поэтому сломанный компонент виден только белым экраном, а `node --check`
  ловит лишь синтаксис. Тест выполняет `.jsx` с заглушкой React (никакого
  Babel и npm) и смотрит, что собралось.
- **Пять вкладок вместо девяти.** `TabKnowledge` = глоссарий + память переводов
  (две справочные базы одной области), `TabAnalysis` = смета + итог + замечания +
  доска + статистика (все отвечали на вопрос «что не так и во что обойдётся»).
  Старые ключи вкладок живы в `tabMap`: на них ведут ссылки изнутри страниц.
- `load_state()` при битом `state.json` сохраняет его как `state.corrupt-*` и
  поднимает свежайший бэкап из `data/backups/` (48 почасовых копий).
- PDF-экспорт не реализован. DOCX бывает двух видов: обычный (собирается
  с нуля, оформление исходника не переносит) и `docx_layout` — 1в1
  в исходном файле, см. ниже. XLSX собирается по-настоящему (openpyxl).
- `seg["risk"]` — длина сегмента (`words > 30 → high`, `> 8 → medium`), а НЕ медицинская
  опасность. Не подписывай его как «риск по содержанию»: в медицинском инструменте это
  опасное враньё. Настоящий `risk_score` даёт только медицинский QA.
  **Писать в `risk` результат проверки нельзя.** Medical QA ставила туда свою
  оценку и тем перетирала длину, по которой раньше выбирался движок. Движок теперь

- **Заверенное человеком чинится точечно и только по разрешению.** Проверки
  (back-check, termcheck, Medical QA) берут подтверждённые сегменты наравне
  со всеми — фильтра по статусу у них нет, и находка на заверенном тексте видна
  всегда. А вот переписать его вправе только ремонт и только по галочке
  `include_confirmed` («чинить подтверждённые» в строке шага). Три правила,
  которые нельзя ослаблять:
  1) **разбор обязан читать тот же флаг, что и прогон** (`_plan_step`) — иначе
     смета обещает одно, а работа делает другое, и это ровно та беда, ради
     которой состав считает сервер;
  2) **флаг доезжает ТОЛЬКО до шага ремонта** (`_job_chunk_full` гасит его
     остальным). Отдай его переводу — и одна галочка перегонит заверенные
     сегменты заново, целиком и за полную цену, вместо правки по находкам;
  3) **взведённый флаг виден у главной кнопки и не переживает ни вкладку,
     ни смену проекта.** Переключатель живёт в раскрытой строке ремонта —
     строку сворачивают, а «Перевести и проверить» продолжает снимать отметки
     «подтвердил человек». Поэтому состояние НЕ хранится в localStorage
     (это разрешение на один прогон, а не настройка), гасится при смене
     проекта и, пока включено, названо предупреждением прямо над кнопкой;
  4) чинится не «весь проект заново», а сегменты с конкретными находками,
     включая расхождение с утверждёнными терминами (`glossary_impact`
     пересчитывается при любой правке глоссария, поэтому одобренный термин
     сам приводит в список все затронутые сегменты — по всему документу).

  в `prevTarget`, статус становится `review`, отметка `confirmedBy` снимается.
  На экране «Анализ» такие сегменты живут в своей корзине
  (`human.confirmedFindings`), а не в «оценке ниже порога»: там они выглядели
  машинными и ждали бы вечно.
- **Спор проверки с приказом глоссария разрешается всегда в пользу глоссария.**
  termcheck смотрит только на перевод и не знает, что термин пришёл из
  глоссария, поэтому он вправе забраковать УТВЕРЖДЁННЫЙ термин. Дальше
  происходит одно и то же: `_gloss_misses` молчит (термин в тексте есть),
  находка уходит в ремонт, модель получает в промпте два взаимоисключающих
  требования, а `_repair_scores` считает нарушенные утверждённые термины
  БЕСПЛАТНО и всегда — замена приказного термина поднимает счётчик, и правка
  откатывается. Машина тут бессильна по построению, поэтому спор виден
  отдельной корзиной в `/analysis` (`human.termcheckDisputes` — список

  переписал текст (перевод, ремонт, переперевод), и всегда на `review`.
- **Экспорт «как в оригинале» (`format: "docx_layout"`) не собирает документ,

  строит документ с нуля и не переносит из исходника ничего. Поэтому файл
  хранится (`data/sources/{pid}.docx`), а выгрузка открывает его и пишет
  перевод в абзацы. Всё, чего не тронули, остаётся байт в байт: 162 картинки
  учебника фтизиатрии выходят из экспорта побайтово теми же — **кроме тех,
  куда мы намеренно вписали перевод надписи** (см. «Текст на картинках»);
  их число называет отчёт экспорта (`img_repainted`).
  **Якорь сегмента — НОМЕР абзаца** в порядке `body.findall('.//w:p')`, а карта
  «абзац → сегмент» лежит ФАЙЛОМ рядом с исходником (`data/sources/{pid}.json`),
  а не в `state.json`: файл состояния целиком лежит в памяти и переписывается
  при КАЖДОМ сохранении, а карта на 2670 сегментов весит десятки килобайт —
  это лишний мегабайт записи на каждую правку одного сегмента. В проекте
  остаётся только отметка `sourceDocx`, и она **часть опознания**: номера
  проектов переиспользуются (`id = max + 1`), поэтому проект без отметки
  исходника не имеет, чей бы файл ни лежал на диске. Удаление проекта уносит
  и файл.
  **Список абзацев обязан быть ПОЛНЫМ** (`_docx_paragraphs` отдаёт и пустые,
  и чисто цифровые): выброси из него хоть один — и номера уедут, а переводы
  встанут по всему документу не на свои места. Отбор в сегменты идёт отдельно
  (`_docx_units`), и соседний повтор — это один сегмент с ДВУМЯ якорями:
  раньше он просто выбрасывался, а при выгрузке перевод должен встать в оба
  абзаца.
  **В ВЫЧИСЛЯЕМЫЕ поля и в скрытый текст писать нельзя** (`_para_slots`
  пропускает `w:instrText`, `w:webHidden`, `w:vanish`, чужие вложенные `w:p`
  и результат полей из `FIELD_COMPUTED`). В строке оглавления там лежит номер
  страницы — тот самый
  «85», который старый импорт приклеил к заголовку; считает его Word, и писать
  туда перевод значит сломать оглавление.
  **А вот результат ОСТАЛЬНЫХ полей — обычный видимый текст, и он переводится.**
  Раньше пропускалось любое поле целиком, и в английском учебнике одна строка
  оставалась русской: у поля `TOC` результат растянут на десятки абзацев,
  а метку (`fldChar begin` + `instrText`) несёт только ПЕРВЫЙ из них — он один
  и выпадал. Имя поля читает `_field_key` (первое слово инструкции; ключи
  начинаются с обратной косой и именем не бывают), стек открытых полей ведётся
  по абзацу. **Непрочитанное поле считается вычисляемым**: инструкция всегда
  идёт до результата, поэтому к тексту имя уже известно, а писать в то, чего
  не понял, опаснее, чем пропустить.
  **Номера страниц пересчитывает Word, и попросить его об этом обязаны мы**
  (`_refresh_fields`, счётчик `fields_refreshed`). Английский текст короче
  русского — книга худеет с 324 страниц до 302, а в оглавлении остаётся «311»
  от исходника. Своей вёрстки у нас нет, посчитать эти числа нечем; всё, что
  можно, — пометить поля к пересчёту, и делается это ДВУМЯ способами, потому
  что клиенты слушают разное: `w:dirty` на самом поле и `w:updateFields`
  в `settings.xml`. Порядок элементов в `settings.xml` задан схемой и Word
  разборчив — вставка идёт ПЕРЕД первым из `_SETTINGS_AFTER`, а не в конец.
  Пересчёт заодно пересобирает оглавление по ЗАГОЛОВКАМ, а они переведены, —
  то есть чинит и строки, и номера разом. Помечается только то, что движок
  и так считает сам (`FIELD_REFRESH`).
  Номер, попавший в САМ сегмент,
  снимается с перевода (`stats["trimmed"]`) — и только когда подтверждён
  и текстом абзаца, и текстом сегмента, иначе в оглавлении встало бы «85»
  дважды. Сравнивается текст абзаца ЦЕЛИКОМ (`_para_slots` отдаёт его третьим
  значением) — ровно так, как его склеивал импорт: пропущенный номер бывает
  не только в хвосте, и сравнение «то, что можно заменить, плюс хвост»
  оставляло такие строки неразобранными.
  **Выделения ВНУТРИ абзаца переносятся, а не схлопываются** (`_write_para`,
  `_split_target`). Перевод режется на куски по группам оформления исходного
  абзаца, и сумма кусков ВСЕГДА равна переводу целиком: границы — это индексы
  одной строки, идущие по возрастанию от нуля до конца, потерять или задвоить
  текст нельзя по построению. Границы ставятся тремя способами, и два первых —
  не догадка:
  1) **кусок, который перевод сохраняет дословно** (`_verbatim_token`:
     латинское название вида, аббревиатура, число) ищется в переводе как есть;
  2) **знак препинания** (`_delim_class`): в исходнике выделение кончается
     на нём почти всегда — «13 ГЛАВА.», «Клиника: », «ПЦР – полимеразная…».
     Сравниваются КЛАССЫ знаков, а не символы: тире и кавычки в переводе
     другого начертания. Число ищется по ЦИФРАМ, а не по записи, — «1,3»
     и «1.3» одно и то же;
  3) доля длины — запасной ход, и он всегда подтягивается к границе слова:
     половина слова жирной это не «примерно так же», а брак.
  Что осталось догадкой, решается **по переводу, а не по исходнику**
  (`_snap_word` возвращает признак): знак в исходнике есть почти всегда,
  а найтись в переводе рядом с расчётным местом может и не найтись — считать
  такое совпадением значит отчитаться цифрой, которой не было. На учебнике
  из 2687 абзацев 2362 однородны, 225 размечены точно и 101 содержит хоть
  одну приблизительную границу; число показывается человеку после сборки.
  **Отпечаток оформления — только ВИДИМОЕ** (`_vis_sig`, набор `_VIS_RPR`).
  Word сам режет текст на прогоны и расставляет `w:lang` (каким языком
  проверять орфографию), `w:noProof`, `w:bCs`/`w:szCs`: на учебнике 255 абзацев
  из 678 «разного оформления» различались ТОЛЬКО этим. Ещё 96 — `w:spacing`
  и `w:kern`, микроподгонка межбуквенного расстояния под ширину строки;
  строка после перевода всё равно другой длины, и переносить её не только
  незачем, но и вредно. Резать перевод там, где резать нечего, — прямой ущерб.
  **Колонтитулы входят в разбор** (`_docx_flat_paragraphs`): они лежат
  отдельными частями пакета и в `body` не попадают, поэтому бегущий заголовок
  без этого остаётся на языке оригинала. Обход по ЧАСТЯМ, а не по секциям —
  секции делят колонтитулы между собой, и обход по секциям выдал бы один абзац
  несколько раз. **Тело идёт первым**, и это инвариант: номера абзацев тела
  от появления колонтитулов не сдвинулись, поэтому карты, записанные раньше,
  остались верны — экспорт принимает и прежний счёт абзацев (только тело).
- **Текст, впечатанный в картинки (`backend/image_text.py`, `kind: "images"`).**
  Часть текста живёт ТОЛЬКО в растре: подписи под рисунками, схемы, куски
  сканов. Абзацного якоря у него нет, поэтому до разбора он не переводится
  вовсе, а в выгрузке 1в1 остаётся на языке оригинала. Отсюда **второй вид
  якоря — «часть пакета + номер блока»**; карта лежит в том же sidecar-файле
  рядом с исходником (`data/sources/{pid}.json`, ключ `images`) и по той же
  причине, что карта абзацев: `state.json` целиком в памяти и переписывается
  при КАЖДОМ сохранении.
  **Работа делится надвое, и это не косметика.** ГЕОМЕТРИЮ даёт локальный
  детектор (RapidOCR): по рамке потом стирают и пишут, а зрячая модель
  координаты выдумывает — ошибка в рамке означает заплатку посреди снимка.
  ТЕКСТ даёт зрячая модель: распознавалка, идущая с детектором, знает
  китайский и английский, а «пиопневмоторакс» вернула как «WONHeBMOTOpaKC».
  Разбор кэшируется ПО СОДЕРЖИМОМУ картинки (sha), поэтому повторный заход
  не платит за уже прочитанное и не заводит те же сегменты второй раз.
  **Найденное становится ОБЫЧНЫМ сегментом** — с тем же переводом, теми же
  проверками и теми же корзинами разбора: отдельная сущность означала бы
  второе место, меняющее текст, и второй набор проверок. Сегмент встаёт
  рядом со своей картинкой, а не в конце списка (`_image_anchor_sid`):
  без соседей его переводят без контекста.
  **Надпечатка аппарата сегментом не становится никогда.** На 38 снимках
  учебника из 51 с текстом в рамках лежат фамилии пациентов, даты
  исследования и настройки томографа — это не текст документа, а в случае
  фамилий ещё и персональные данные, которым нечего делать в TM и в очереди
  терминов. Признак ставит модель при чтении (`overlay`); правило о буквах
  (`is_noise`) закрывает только то, что видно без модели («250MA», «kV 120»).
  **Посмотреть не удалось — это «не знаю», а не «текста нет».**
  `detect_lines` возвращает None и без движка, и на нечитаемой картинке;
  разбор помечает такую `unreadable` и называет их число. Пустой список
  означал бы «надписей в схеме нет» — враньё там, где на ответ полагаются.
  **В экспорте перевод возвращается в картинку, только если фон однороден**
  (`flatness` ≥ `IMG_FLAT_MIN`) и кегль остаётся читаемым. Иначе перевод
  уходит ОТДЕЛЬНЫМ абзацем-подписью сразу за картинкой: заливка поверх
  рентгенограммы — порча документа. Никакой приписки вроде «текст на
  рисунке» подпись не несёт: это был бы выдуманный текст, да ещё
  на неизвестно каком языке. Числа обоих исходов — в отчёте экспорта.
  **Заливка идёт ДО текста, вся разом**: рамки соседних блоков законно
  пересекаются (заголовок над двумя колонками), и заливка второго блока
  стирала бы уже написанный перевод первого — с отчётом «оба написаны».
  **Формат части пакета менять нельзя**: тип объявлен в `[Content_Types].xml`
  по РАСШИРЕНИЮ, поэтому JPEG сохраняется JPEG, PNG — PNG, а вместе с ними
  сохраняются EXIF, профиль цвета и разрешение (без EXIF фотография ляжет
  боком). Палитровый PNG возвращается в палитру: RGB — это пятикратный вес
  на ровном месте. Исходник на диске не трогается никогда — перерисовка
  живёт только в копии экспорта.
  **Разбор переживает повторную привязку исходника.** Карта абзацев и карта
  картинок лежат в одном файле, но пишутся из разных мест: пока `_store_source_docx`
  не сохраняла второе, нажатие «Заменить» уносило минуты разбора, оплаченный
  текст и связь с сегментами — а сами сегменты оставались в проекте, и их
  перевод исчезал из выгрузки без единого счётчика. Приложили ДРУГОЙ файл —
  это ловится отпечатком картинки при выгрузке (`img_stale`), а не молчаливой
  потерей работы. По той же причине `/source` и `/images/forget` отвечают 409,
  пока идёт разбор: два писателя одного файла — это потеря работы одного из них.
  **Сегмент подтверждает себя ЯКОРЕМ, а не номером** (`_image_seg_of`): номера
  переиспользуются (`max(id) + 1` после сноса выдаёт те же числа), и по одному
  номеру блок цеплялся к чужому сегменту, оставался без перевода и выпадал
  из выгрузки молча.
  **Снос распознанного не выбрасывает оплаченное.** `/images/forget` убирает
  сегменты, но оставляет геометрию и прочитанный текст: повторный заход заводит
  сегменты заново и бесплатно. Выбросить текст можно явным `wipe` — отката
  у команды нет, поэтому это отдельное решение человека, а не побочное действие.
  **Оборванный ответ модели не выбрасывается целиком** (`_image_read_parse`):
  на отсканированной странице ответ упирается в потолок и рвётся на середине,
  а следующий заход с той же нарезкой оборвался бы там же — оплачиваемая
  карусель. Берём законченные блоки, остальные остаются нерешёнными.
  **Надпечатку отсеивает модель, а спорное решает человек — и решение
  ЗАПОМИНАЕТСЯ** (`POST /api/projects/{pid}/images/{sid}/overlay`). На боевом
  учебнике из 41 заведённого сегмента 15 оказались строками прибора («LINEAR
  DISTANCE: 004.43cm», «kV 120.0 mA: 283», «IPAP DOKTOR HAKIMOV M» — фамилия
  врача, которой нечего делать в памяти переводов). Дальше машиной это не
  отсеивается, и пробовать не надо: правило «на картинке большинство надписей —
  надпечатка» на тех же данных убило бы законную подпись «Диссеминированный
  (милиарный) туберкулёз», а «нет букв языка оригинала» — латинское название
  вида. Кнопка стоит в карточке сегмента рядом с куском картинки, метка ложится
  на БЛОК, и следующий разбор сегмент заново не заводит. Бесплатное согласие
  между картинками (`_image_harmonize`) снимает только ТОЧНЫЕ повторы: строки
  прибора различаются показаниями, и на них оно не срабатывает — обещать
  обратное нельзя.
  **Решение по надписи обратимо в ОБЕ стороны, и след человека вечен.**
  `POST …/images/{sid}/overlay` — «это надпись аппарата» (убрать сегмент),
  `POST …/images/restore` — «это текст документа» (снять метку и завести
  сегмент), `GET …/images/blocks?skip=overlay|noise|none` — что именно отсеяно,
  списком и с кроп-картинкой по каждой строке. Без списка «Отсеяно: 230» —
  число, которое человеку нечем проверить, а отсев делает модель и ошибается
  в обе стороны. На блоке остаётся `by` (`model` | `human`), и `_image_harmonize`
  блоки с `by: "human"` НЕ ТРОГАЕТ: иначе система слушалась бы человека ровно
  в одну сторону — пометку «надпечатка» согласие не отменяет никогда, а снятую
  им стирало бы каждым разбором. По тому же `by` человек отличает в списке свои
  решения от машинных, иначе разберёт их заново.
  **Возвращённый сегмент встаёт ЗА своими соседями по картинке** (последний
  сегмент той же части с меньшим номером блока): иначе в промпт перевода ему
  достаются чужие соседи, а на одном якоре с двумя картинками он садится
  в середину первой. Номер абзаца-якоря пишется в карту при разборе
  (`rec["paras"]`) — читать ради него весь .docx на единственном воркере
  незачем.
  **Число сегментов проекта приходит в разборе прогона** (`projectSegments`
  у `/run-plan`). Сегменты заводятся и мимо вкладки редактора — например,
  разбором картинок с экрана экспорта, — и тогда состав прогона обещает
  «41 непереведённый», а в таблице их нет и выбрать их нечем. Редактор
  сверяет число и подтягивает проект один раз; отметка «за каким составом
  уже ходили» — по составу, а не по факту запроса: замок «идёт запрос»
  откладывал синхронизацию навсегда.
  **Модель чтения выбирается на экране, и цена считается СЕРВЕРОМ**
  (`_image_est_by_model` — {модель: цена за ЭТОТ разбор}). Цена за миллион
  токенов человеку ничего не говорит о том, во что обойдётся вот эта книга,
  а цифра в `.jsx` была бы вторым прайс-листом рядом с настоящим.
  **Привязка исходника считает только АБЗАЦНЫЕ сегменты**: сегменты картинок
  сбивали окно двухуказательного поиска и раздували знаменатель порога
  «совпало меньше половины», из-за чего родной файл отклонялся как чужой.
  Движок ставится ОТДЕЛЬНОЙ строкой (`pip install --no-deps
  rapidocr-onnxruntime`): своей зависимостью он тянет `opencv-python`,
  которому нужен `libGL.so.1`, а на сервере графики нет — тот же модуль даёт
  `opencv-python-headless` из `requirements.txt`.
- **Исходник прикладывается и к готовому проекту (`POST /api/projects/{pid}/source`).**
  Проекты, импортированные до появления формата, файла не сохранили, а
  переводить их заново нельзя — там оплаченная работа. Сопоставление идёт
  ПО ТЕКСТУ (`_map_source_to_segments`, окно `_SOURCE_LOOKAHEAD`), а не по
  номерам: правила отбора абзацев со временем меняются, и жёсткое «первый
  абзац = первый сегмент» после любой такой правки посадило бы перевод
  на чужие строки молча и по всему документу. Чужой файл виден по числу
  совпадений и отклоняется (порог — половина сегментов, снимается `force`).
  Переводы, проверки и статусы не трогаются вообще.
- **Область записи: языковая пара + тематика.** Глоссарий и TM одни на сервис,
  проекты разные. `_get_context` отдаёт только записи из области проекта
  (`_project_scope`), TM — только свою языковую пару. Записи без полей `lang`/`domain`
  читаются как `RU→EN` + `medical` (весь исторический импорт именно такой), поэтому
  массовой миграции нет — не добавляй её, это лишние сотни килобайт в каждом
  сохранении `state.json`. Новые записи область получают всегда.
- **Автоодобрение кандидатов (`_auto_verdict`).** Однозначным считается только то,
  что подтверждают сигналы, не зависящие от языка и тематики: единственность варианта
  в очереди, согласие НЕЗАВИСИМЫХ сегментов-доноров (`cand["segments"]`, ключ
  `"проект:сегмент"` — номера сегментов уникальны лишь внутри проекта) и чистые оценки
  чужих прогонов (`_machine_clean`: back-check ≥ порога, termcheck без находок, текст
  не переписан авторемонтом, termcheck не пропущен как «нечего проверять»).
  **Независимость считается по РАЗНЫМ исходникам.** Сегменты с `route: "DUPLICATE"`
  и с `propagatedFrom` донорами не считаются вовсе (перевод скопирован, а не получен
  заново), а на приказ нужны доноры с разным текстом оригинала: один и тот же
  заголовок, переведённый трижды, — это одно решение, а не три подтверждения. Кандидат `conflict` не одобряется никогда (у него нет
  готового перевода), `audit` — не меньше чем с двух доноров: это мнение модели
  о собственном переводе. `dry_run=True` — режим по умолчанию, он ничего не меняет.
  **Смысловая сверка (`_meaning_check`)** — последние ворота перед записью:
  судья пачками по `AUTO_MEANING_CHUNK` отвечает, ТО ЖЕ ли это понятие —
  единственный вопрос, которого не задаёт никто другой («Анизакидоз →
  Anisakis» проходит корпус, termcheck и согласие сегментов разом). Явное
  «не то понятие» отклоняет кандидата совсем — даже подсказкой ложный друг
  вреден; причина хранит обратный смысл НА ЯЗЫКЕ ОРИГИНАЛА. «Не знаю»
  (сбой, пара не разобрана) не одобряет и не блокирует — тот же закон, что
  у `attested()`. Платно, поэтому как корпус: по умолчанию только при
  применении (`meaningPending` в разборе), потолок `AUTO_MEANING_MAX`.
  Отклонённые входят в пачку (`rejectedMeaning`) и возвращаются в очередь
  её откатом.
- **Аудит глоссария (`POST /api/glossary/audit`)** задаёт тот же вопрос
  записям, которые УЖЕ стоят приказом: сверка при автоодобрении сторожит
  вход, а приказывают модели и гонят ремонт те, что попали туда раньше.
  Находка **понижается до подсказки, а не удаляется**: перевод остаётся,
  запись остаётся видна, но перестаёт приказывать и быть основанием ремонта.
  **Понижается только своё предположение.** Уровень «приказ» запись могла
  получить по умолчанию миграции («её нет в массовом импорте — значит
  добавлена руками») — на боевых данных так вышло у 670 записей без единого
  следа. След решения человека (`_human_touched`: `origin: confirmed:*`,
  «уточнено вручную», `autoBatch`/`byOverride`) делает запись неприкосновенной:
  её только помечают. Порядок проверки — по вреду: сначала расходящиеся
  с переводом в этом проекте. Понижение идёт пачкой и откатывается
  `undo_auto_approve`; `prevOrigin` обязателен — без него откат снял бы
  происхождение записи.
  **`include_human` — разрешение понизить и одобрения человека пачкой.**
  Разбирать список поштучно на сотне записей невозможно, а сама машина чужое
  решение не отменяет никогда. Значит нужна не автоматика вместо человека,
  а его явное разрешение на один заход — и тогда список ведёт вердикт судьи,
  а не перечень слов в коде. Записи с `meaningKept` не трогаются и здесь:
  человек уже возвращал их из понижения, и переспрашивать значит не считать
  его ответ ответом. Понижение пачкой сразу возвращает переписанные сегменты
  (`_revert_repairs_bulk` — ОДИН проход по сегментам на ВСЕ записи; поштучный
  откат на трёхстах записях означал бы триста проходов по проекту).
  **Вердикт кэшируется НА ЗАПИСИ** (`g["meaning"]`, отпечаток пары
  `_meaning_pair`, производный `_meaning_stale` — как `target_hash` у
  back-check).
  **Набор вопросов версионирован (`MEANING_VERSION`), и версия входит
  в устаревание.** Когда к «то же ли это понятие» добавился вопрос «годится ли
  правилом», полторы тысячи записей с готовым вердиктом остались с прежним
  набором: отпечаток пары совпадал, устаревшими они не считались, и «Досверить
  новые» находило ноль. Оставался только `force`, а он упирался в потолок и
  переспрашивал одни и те же первые восемьсот — до хвоста не доходя НИКОГДА.
  Меняешь промпт сверки — поднимай версию, иначе новый вопрос не задаётся.
  **Переспрос не переворачивает готовый вердикт с одной попытки.** Судья
  на границе «годится / не годится» отвечает неустойчиво, и «Переспросить всё»
  превращалось в переброс монеты: каждый заход находил новые записи
  на понижение, хотя и пара, и вопрос те же — на боевых данных это дало четыре
  пачки понижений подряд (12, 13, 6, 4) и ощущение нескончаемой работы.
  Разошёлся с прежним ответом — пара спрашивается ТРЕТИЙ раз и берётся
  большинство; платит за это только сама спорная пара, остальные идут одним
  ответом. Молчание третьего голоса прежний ответ не отменяет. В любом исходе
  вердикт клеймится свежим, иначе следующий заход потянул бы ту же пару снова.
  Что считать находкой — один предикат `_verdict_bad` на запись вердикта
  и на разбор: разойдись они, аудит показывал бы одно, а понижал другое.
  **Пустота от судьи — это «не знаю», и приходит она ДВУМЯ путями:** ключа нет
  (вердикты прежней версии промпта) либо явный JSON `null` — так модель и
  выражает неуверенность. Проверка «ключ есть» ловила только первое, а
  `bool(None)` превращала второе в твёрдое «понятие другое»: запись понижалась,
  а откат переписывал сегменты по замечанию, которого не было. Сверять надо
  `is None`, а не наличие ключа.
- **След решения человека ставит и ручная правка глоссария** (`save_term`
  пишет «уточнено вручную»). Без него `_human_touched` не отличает правку
  руками от записи массового импорта, и аудит понижает её без разрешения —
  то есть машина молча отменяет то, что человек только что вписал сам.
- **Понижение записывает `prevTgt` НЫНЕШНИМ переводом.** Само оно перевода
  не трогает, но `undo_auto_approve` читает `prevTgt` безусловно, и значение,
  оставшееся от прошлой пачки, воскресило бы перевод, от которого давно
  отказались.
- **Откат правок ремонта требует, чтобы в сегменте стоял ИМЕННО текст ремонта**
  (`_repair_tried`). Иначе перевод правили после него — руками или другим
  прогоном — и подстановка `repair.from` выбросила бы чужую работу молча.
  Проверка идёт ПОСЛЕ сверки претензии: до неё она отсеивала бы и сегменты,
  к этой записи отношения не имеющие.
  Порядок перебора устойчив (вес по расхождениям, затем сам термин): вес
  меняется после каждого понижения, и без второго ключа потолок отрезал бы
  каждый заход ДРУГОЙ хвост. Остаток (`pending`) считается по свежести
  вердикта, а не арифметикой «сколько отобрали минус сколько спросили»:
  судья мог не ответить про часть пар. Без кэша аудит спрашивал ВСЕ записи каждым запуском, а судья
  на границе «то же понятие / не то» отвечает неустойчиво: список на понижение
  каждый раз выходил новый, и понижать приходилось бесконечно. Поэтому вердикт
  пишется даже при `dry_run` (это кэш, а не решение), «не знаю» не пишется
  никогда, а переспросить всё можно только явным `force`.
  **Откат понижения помечает запись `meaningKept`** и делает её
  неприкосновенной для `_human_touched`: человек решил оставить приказ,
  и предлагать понижение снова — тот же бесконечный круг.
- **Проверка терминов НОМИНИРУЕТ, а не понижает** (`_note_term_disputes`,
  уровни `TERMCHECK_DISPUTING` — только `critical`/`major`, и это НЕ то же
  самое, что `TERMCHECK_ACTIONABLE`, по которому работает ремонт. Право
  переписать текст и право усомниться в решении человека — разные права:
  номинация делает вердикт сверки смысла устаревшим, то есть заказывает
  платный переспрос судьи, и ставит перед человеком выбор «неверна запись
  либо неверна проверка». От стилистической придирки это ложная дилемма,
  а termcheck на уровне `minor` самый шумный).
  Находка termcheck на слове, которое и есть приказной перевод, растит
  счётчик `disputed` у записи и делает её вердикт устаревшим — следующий
  аудит спросит про неё заново. Понижать оттуда напрямую нельзя: termcheck —
  один вызов модели, и на «infiltrate → induration» ошибается именно он;
  решает по-прежнему вопрос «то же ли это понятие». Метку ставит настоящая
  запись глоссария через `_glossary_entry`: `_get_context` отдаёт КОПИИ,
  и пометка на них пропадает вместе с ними. Под локом — termcheck идёт
  в рабочих потоках, а глоссарий общий.
  Любая пачка откатывается целиком (`/api/term-queue/auto-approve/{batch}/undo`)
  по `autoBatch` и сохранённым `prevTgt`/`prevTier`; автоматика без отката недопустима.
- **Решение по кандидату — про термин, а не про карточку.** Дедупликация очереди
  идёт по паре, с которой кандидат РОДИЛСЯ (`_cand_pair`, поля `origSrc`/`origTgt`):
  одобрение вписывает в `src`/`tgt` решение человека (у `conflict` перевод рождается
  пустым и заполняется только им), и без этой памяти следующий `_harvest_terms`
  не узнавал бы решённого кандидата — одобренный термин возвращался в очередь
  новым. Одобрение закрывает и остальные ОЖИДАЮЩИЕ карточки про тот же термин
  в той же области (`_close_same_term`); отклонение — нет: «эта пара неверна»
  не равно «с термином разобрались». Подрезка очереди снимает решения человека
  последними (`_human_decision`) — на них держится «этот вопрос уже задавали».
  **Одной пары для этого мало, и в ключе она не последняя.** Пары совпадают,
  только если следующий прогон предложил ровно тот же перевод; на деле он
  предлагает свой, а находка termcheck приходит другим `kind` — ключ выходит
  новый, и утверждённый термин всплывал нерешённым КАЖДЫМ прогоном. Поэтому
  `_queue_term_locked` перед заведением карточки спрашивает, отвечен ли вопрос
  вообще: решением человека про этот термин (`_term_answered`, ищет и по
  нынешнему `src`, и по `origSrc` — одобрение вправе исправить сам термин) либо
  записью глоссария уровня **приказ**. Отвечен — карточки нет, а чужой вариант
  дописывается в `reasked` решения (потолок `TERM_REASKED_MAX`): проглотить
  несогласие молча нельзя. Запись уровня **подсказка** вопрос НЕ закрывает —
  массовый автоимпорт («задний → rear») ловится conflict-кандидатами, ради
  этого они и заведены. Отклонение тоже не закрывает: см. выше.
  Накопленное прежним кодом снимает `_migrate_term_queue` — ПОЗДНИМ проходом
  при старте, а не из `_apply_migrations`: та зовётся при импорте раньше, чем
  определены `_norm_key`, `_cand_pair` и `_human_decision`, а повторять их
  правила на месте — значит однажды разойтись с ними в том, что считать
  одним и тем же термином.
- **«Одобрить и применить» не запирается на нуле терминов.** Кнопка гасла,
  когда автоодобрению нечего одобрять, — а расхождения с УЖЕ утверждёнными
  терминами чинит та же задача (`_job_run` считает состав из `glossary_impact`
  ПОСЛЕ одобрения и работает при пустой пачке). Человеку оставался только
  переперевод: вдвое дороже и без проверок. Теперь кнопка называется
  «Применить к N сегм.», а состав берётся из того же отчёта, что показывает
  соседняя карточка.
- **Сверка спрашивает ДВА вопроса, и второй не менее важен.** `same` — то же
  ли это понятие. `rule` — годится ли пара ПРАВИЛОМ на весь документ: «Клинику →
  clinical practice» верен в «внедрено в клинику» и неверен в «направлен
  в клинику», а «частоте → frequency» — падежная форма вместо словарной.
  Понятия при этом совпадают, и один только `same` такое пропускает — а запись
  между тем принуждает модель во всех сегментах разом. Отсутствие поля `rule`
  читается как «не знаю» (так выглядят вердикты, записанные прежней версией),
  и одобрением не считается.
- **Ручное одобрение кандидата проходит ту же сверку, что и машинное.**
  Раньше этот путь не проверялся ВООБЩЕ: `approve_term_candidate` писал приказ
  напрямую, пока автоодобрение шло через корпус и сверку смысла. Выходило
  наоборот — решения машины проверялись строже решений человека, который
  целевого языка может не знать и оценить пару не в состоянии. Замечание
  возвращается ДО записи (`written: false`, в глоссарий ничего не пишется,
  кандидат остаётся нерешённым: человек замечания ещё не видел), одобрить
  вопреки ему можно полем `confirm`. Вердикт кладётся на запись, поэтому аудит
  глоссария его не переспрашивает платно. Нет ключа — нет проверки, но и нет
  запрета: тот же закон, что у корпуса.
- **Понижение по решению человека (`POST /api/glossary/demote`).** Отдельно
  от `save_term` намеренно: там действует правило «правка руками = приказ»
  (меняя перевод, человек за него ручается), а здесь намерение обратное.
  Нужно потому, что сверка смысла находит неверные приказы, но записи со
  следом решения человека не понижает — чужое решение машина не отменяет.
  Без этой двери находка показывалась и ничем не кончалась, а именно на такие
  записи приходится больше всего сегментов. Удаления в списке сверки мало:
  перевод может быть верен В КОНТЕКСТЕ и негоден как правило на весь документ —
  подсказка ровно это и означает. `meaningKept` при понижении снимается:
  человек решил обратное.
  **Понижение снимает ПОВОД чинить, но не отменяет уже сделанного.** Запись
  уходит из `_gloss_misses` и `/glossary-impact` (оба считают по приказам),
  то есть сегменты перестают числиться нарушением и ремонт к ним больше
  не пойдёт. А те, куда ремонт термин уже вписал, так и остались переписанными:
  `_repaired_by_term` их считает по тексту претензии в `repair.issues`, и ответ
  называет их число. Молчать нельзя — человек уверен, что отменил правило
  целиком. Откатывать их автоматически тоже нельзя: прежний текст лежит
  в `repair.from`, но заменить им нынешний значит переписать перевод
  ВТОРОЙ раз без единой проверки. Возвращает их отдельная команда
  `POST /api/glossary/revert-repairs` — **единственная во всей системе, что
  меняет текст БЕЗ вызова модели**. Так можно ровно потому, что она ничего
  не сочиняет: подставляется `repair.from`, тот самый текст, что стоял
  до правки и у которого были свои проверки. Два случая и смешивать их нельзя:
  претензия была ЕДИНСТВЕННОЙ причиной правки — возвращаем; причин было
  несколько — не трогаем (откат унёс бы верные исправления чисел и калек),
  а снимаем `repair.source_hash`, и сегмент снова доступен ремонту. Проверки
  после отката становятся устаревшими сами: их хеш описывает отвергнутый текст.
  Сегменты, где `repair.from` пуст, называются поимённо — вернуть их нечем,
  и молчать об этом нельзя.
- **Вынос массового импорта (`POST /api/glossary/purge`).** `DELETE /api/glossary`
  работает по ОДНОЙ записи, а импорт — десять тысяч: поштучно их не выносят,
  и без этой команды «удалить всё» делалось бы руками по файлу состояния.
  **`multi_variant` выносит записи, хранящие НЕСКОЛЬКО вариантов перевода**
  («аппендицит → appendicitis; ecphyaditis», «биоптат → biopsied; material»).
  Это не перевод, а строка из словарной статьи: модель получает её одной
  подсказкой целиком, и на боевом проекте 267 раз в перевод садился ПЕРВЫЙ
  вариант — а первый там сплошь и рядом хуже второго («aspergillomycosis»
  вместо «aspergillosis», «biopsied» вместо «material»). Починить выбором
  варианта нельзя: какой верен, знает предметная область, а не разделитель.
  Разделителем считается ТОЛЬКО точка с запятой (`_VARIANT_SEP`): на боевом
  глоссарии она стоит в 157 подсказках и ни в одной приказной записи. Косая
  черта им не считается — она часть самого термина («HIV/TB coinfection»,
  «helper/suppressor T-cell balance»), запятая тоже — ею перечисляют дозировки
  («Ciprofloxacin (250, 500, 750 mg)»).
  Три предохранителя: `dry_run` по умолчанию; записи со следом решения
  человека (`_human_touched`) не выносятся НИКОГДА, и сколько таких — сказано
  в ответе; вынесенное целиком уходит файлом в `data/backups/` и возвращается
  `/purge/{stamp}/undo` (массовое удаление без отката недопустимо — тот же
  закон, что у пачек автоодобрения). Откат не затирает запись, появившуюся
  после выноса. `unused_only` считает применимость тем же `_term_match`, что
  и инъекция в промпт, но обходом ПО СЕГМЕНТАМ (`_used_term_ids`), а не по
  записям: поштучно это 9502 × 2670 проверок регулярками — минуты работы
  ЕДИНСТВЕННОГО воркера, то есть запрос отваливается по таймауту, а сервис
  на всё это время недоступен всем. Через индекс — 15 секунд. Кандидаты
  берутся индексом напрямую, а НЕ через `_get_context`: он оставляет
  пятнадцать лучших записей на сегмент, и не влезшие оказались бы
  «неиспользуемыми», то есть вынесенными вместе с работающими. **На готовый перевод вынос подсказок не влияет ничем**:
  расхождения и ремонт считаются только по приказам (`_verified_hits`).
  **`tier: "verified"` выносит приказы, доставшиеся импорту по умолчанию
  миграции** («записи нет в массовом импорте — значит добавлена руками»).
  Это предположение машины, а не решение человека: на боевых данных так
  вышло у 452 записей вроде «алкилполигликозид → alkylpolyglycoside» в учебнике
  фтизиатрии. Одобренное из очереди и правленое руками при этом не трогается —
  их защищает `_human_touched`.
- **Обрывок фразы кандидатом не становится** (`_looks_like_term`, виды
  `extract` и `segment`). Промпт извлечения просит словарную форму, но просьба
  не проверка: модель выдавала «в лёгких → in the lungs» и «у больного → The
  patient», и такие записи потом держали балл back-check как «потерянный
  термин». Правило одно и намеренно узкое: запись не НАЧИНАЕТСЯ отдельно
  стоящим служебным словом. Конец не проверяется вообще («Гепатит В»,
  «Гепатит С», «Витамин С»), первое слово берётся целиком по пробелам
  («В-лимфоцит», «С-реактивный белок»), служебные слова только кириллические
  («in situ» остаётся, а для источника на другом алфавите проверка МОЛЧИТ —
  закон `DOMAIN_RULES`). Широкое «содержит предлог» убило бы «боль в груди»,
  поэтому «имеются у пациента» этим правилом не ловится: такие пары
  останавливает сверка смысла (`rule: false`), приказом они не становятся,
  а балл считается только по приказным записям. Проверка стоит ПОСЛЕ
  дедупликации и `_term_answered`: раньше — и перестали бы расти `hits`
  и `reasked`, то есть система молча глотала бы несогласие. Отсев считается
  (`_TERM_NOT_TERM`) и называется в ответе `/extract-terms`
  (`skipped_not_terms`).
- **Потолок очереди — про размер `state.json`, а не про терпение человека.**
  `TERM_QUEUE_MAX` (переменная окружения, по умолчанию 2500): файл целиком
  лежит в памяти и переписывается при КАЖДОМ сохранении, а ожидающая карточка
  тяжелее решённой — в ней лежат `sampleSrc`/`sampleTgt` по 240 символов,
  которые `_mark_decided` снимает при решении. Прежние 800 на документе
  в 2670 сегментов кончились в первый день: очередь встала у потолка, и каждая
  новая находка стала вытеснять старую — терялась ровно та работа, ради которой
  шёл прогон. Занятость очереди пишется в журнал при СТАРТЕ: о потолке узнавали
  из строки «выброшено N», то есть уже после потерь.
- **Потолок очереди кандидатов считается, а не только пишется в журнал**
  (`TERM_QUEUE_MAX`, `_TERM_DROPPED`). Подрезка зовётся на КАЖДУЮ вставку, и на
  полной очереди это один выброшенный кандидат за раз: прогон 22.08 оставил
  890 одинаковых строк «снято 1», из которых не видно главного — что за прогон
  сбор терминологии потерял 890 находок. В журнал теперь пишется изредка
  и с накопленным итогом, а разница за прогон уходит в его счётчики
  (`terms_dropped`) и в отчёт: это платная работа, ушедшая в никуда.
- **Сбор терминологии идёт с проверенных сегментов, а не сразу после перевода.**
  `_harvest_terms(via="confirmed")` — на подтверждении человеком (там же рождаются
  кандидаты `conflict`), `_harvest_if_clean` — в конце back-check и termcheck, когда
  обе оценки чистые (`via="auto"`, только готовые пары). Висит на обоих прогонах
  намеренно: порядок выбирает пользователь, и собрать может лишь тот, кто отработал
  вторым.
- **Подсказки автоимпорта в промпт перевода НЕ уходят.** Блок «Unverified
  glossary hints» из `_translate_system` убран целиком, и вот на каких числах.
  ПОЛЬЗУ доказать не удалось: подсказки попадали в 2316 сегментов из 2711,
  в среднем 2.6 записи на промпт, и в 72% случаев их вариант оказывался
  в переводе — но «больной → patient» и «мокрота → sputum» модель напишет
  и без подсказки, а отличить «помогла» от «совпала» можно только платным
  сравнением двух прогонов. ВРЕД доказан и конкретен: строго (подсказка стоит
  в переводе И termcheck забраковал ровно это слово) — 15 случаев из 11 414
  вставок, и каждый медицинская ошибка, которой модель послушалась:
  «лимфаденит → adenolymphitis», «пунктат → punctate», «воспалительное → IBD»,
  «микобактерии туберкулёза → Mycobacteria tuberculosis». Чаша весов
  несимметрична: с одной стороны недоказуемая польза, с другой — подмена
  понятия в медицинском переводе. Промпт заодно короче на 130 тыс. входных
  токенов на книгу.
  **Сами записи остаются и работают**: растут в приказ через согласие
  независимых чистых сегментов, ловят расхождения conflict-кандидатами,
  разбираются сверкой смысла. Убрано ровно одно — право НЕВЕРЕННОЙ записи
  влиять на перевод напрямую. Приказные записи (`verified`) уходят в промпт
  как уходили: это контракт с клиентом.
- **Уровни доверия глоссария.** `tier: "verified"` уходит модели приказом
  («use these exact translations»), `tier: "auto"` — подсказкой, которую разрешено
  игнорировать. 9132 из 10022 записей — массовый автоимпорт (`baldwin_*`), и там есть
  «задний → rear»; ровно так и рождалось «rear cyclitis». Плейсхолдеры Google
  подставляются ТОЛЬКО для `verified`: это принуждение мимо всех проверок.
  Ручная правка и одобрение кандидата поднимают запись до `verified`.
- **Соответствие глоссарию (`/api/projects/{pid}/glossary-impact`).** Одобрение термина
  НЕ переписывает готовые переводы — это осознанно. Расхождения собираются отдельно
  (термин в оригинале есть, утверждённого варианта в переводе нет) и переводятся заново
  пакетом по кнопке. Считается только по `tier: verified`: требовать соответствия
  автоимпорту нельзя, модель вправе его игнорировать. Подтверждённые сегменты
  переводятся заново только по явной галочке (`include_confirmed` у `/batch`,
  работает лишь вместе с `force` и списком id). При этом прежний текст уходит
  в `prevTarget`, статус становится `review`, а отметка `confirmedBy` снимается:
  машина не заверяет сама себя. Без галочки такие сегменты называются поимённо
  в `skipped_confirmed` — прогон не имеет права рапортовать «готово», не сделав
  ничего.
- **Индекс глоссария.** `_get_context` без индекса гонял 10 000 регулярок на сегмент
  (10-17 с CPU). Есть `_gloss_index()` по ключам-началам слов — любая мутация глоссария
  обязана звать `_invalidate_gloss_index()`, иначе поиск будет работать по старым данным.
  Шаблоны терминов компилируются один раз и лежат в `_PATTERN_CACHE`: без этого внутренний
  кэш `re` переполнялся десятью тысячами записей и пересобирал регулярки на каждый вызов
  (134 мс на сегмент против 1 мс).
- **Найденная форма обязана быть формой ТОГО ЖЕ слова** (`_same_lexeme`).
  Стем режет слово до 85% букв, и комментарий к порогу обещает, что хвост,
  которым различаются понятия (-ит / -оз / -ома), при этом уцелеет. На шести
  буквах («циклоз» → «цикл») это правда, на одиннадцати перестаёт ею быть:
  стем «туберкулема» — это «туберкуле», и он ловит «туберкулез» со всеми
  формами. На боевом учебнике одна эта запись сработала ложно 1006 раз,
  «Туберкулёма лёгких» — ещё 136, плюс «аллергия → аллергена», «инфильтрат →
  инфильтрации», «алкоголизм → алкоголики»: 1185 ложных совпадений на 875
  сегментах. В промпт перевода при этом уходил приказ «Туберкулема →
  Tuberculoma» на сегменты про туберкулёз — в медицинском переводчике это
  подмена одной болезни другой.
  **На экране этого не было видно, потому что вторая половина ошибки гасила
  первую**: `_tgt_has_term` режет «tuberculoma» до «tuberculo», и
  «tuberculosis» его удовлетворяет, поэтому `_gloss_misses` молчал. Отсюда
  правило порядка: чинить сторону ОРИГИНАЛА первой. Ужесточить сторону
  перевода, не тронув оригинал, — значит объявить 875 сегментов нарушением
  и послать ремонт менять `tuberculosis` на `Tuberculoma`.
  Правило проверки: у записи и у найденной формы должен найтись ОБЩИЙ стем,
  после которого у ОБЕИХ остаётся окончание из закрытого списка словоизменения
  (`_RU_ENDINGS`). «первичный»/«первичного» дают «первичн» + «ый»/«ого» — одно
  слово; «туберкулема»/«туберкулеза» не дают такого стема ни при какой длине.
  Словообразовательных суффиксов в списке нет намеренно — ими понятия
  и различаются. Два исключения, оба чтобы не менять лишнего: найденное
  НАЧИНАЕТСЯ с записи целиком («туберкулёз» → «туберкулёзного») — как
  работало, так и работает; слово не из кириллицы — МОЛЧИМ (закон
  `DOMAIN_RULES`). Замер: снято 1185 ложных совпадений, задето 7 записей
  из 152, верных совпадений среди приказных не потеряно ни одного.
  **Перебираются ВСЕ вхождения, а не первое** (`finditer`, не `search`).
  Стем мог совпасть с другим словом, а настоящая форма стоять следующим:
  «Очаговый туберкулез легких. Туберкулемы выявлены…» — по первому хиту
  запись «Туберкулема» объявлялась бы отсутствующей, и приказ не ушёл бы
  ни в промпт, ни в проверку соответствия. В учебнике фтизиатрии эти слова
  стоят в одном абзаце постоянно, то есть правило гасило бы само себя, молча.
  **Послабление «найденное начинается с записи целиком» действует только
  от `_WHOLE_WORD_MIN` букв.** Короткое слово помещается в начало чужого:
  «Я → являются», «АТ → ателектаз», «желе → железы», «тест → тестостерона»,
  «Умер → умеренными». Порог снимает 706 таких пар и НИ ОДНОЙ у приказных
  записей; «рак → рака» и «нос → носа» при этом проходят обычной проверкой
  окончаний.
  **Чего правило не умеет — названо в докстроке**: беглая гласная
  («лимфоузел» → «лимфоузлы», «ребёнок» → «ребёнка»), разносклоняемые
  на -мя и -анин, глагольные формы. На боевом глоссарии это ~4% снятых пар
  и ни одной приказной записи, то есть цена — потерянная подсказка. Ослаблять
  правило ради них нельзя: любое ослабление возвращает «туберкулема →
  туберкулез».
  **После правки, меняющей состав приказных записей, оценки надо пересчитать**
  — `POST /api/projects/{pid}/backcheck/rescore` с `force: true`. Само оно
  не пересчитается: `_GLOSS_EPOCH` растёт от правки ГЛОССАРИЯ, а не кода,
  а `BACKCHECK_VERSION` тут поднимать НЕ надо — это сняло бы у старых записей
  доверие к отметке `judge_skipped: "hard"` и купило бы вызовы судьи ради
  правки, которая формулу не меняла. На боевых данных пересчёт задел
  4 сегмента: «Туберкулема» почти всегда «переживала» обратный перевод
  по общему стему, и весь вред шёл в промпт перевода.
  **Уже написанные 875 сегментов так и остались написанными под неверным
  приказом**, и это не разобрано ничем: `_gloss_misses` слеп из-за обрезки
  в `_tgt_has_term`, back-check слеп из-за `_stems`. Правка убрала причину,
  а не следствие; разбирать следствие — отдельная работа.
  **Определений «то же слово» стало три, и они расходятся**: подбор термина
  в тексте (стем 85% + `_same_lexeme`, строгое), «пережил ли термин круг»
  (`medical_qa._term_survived` → `_stems` + `_same_word_form`, мягкое) и доля
  выживших слов (`_stems`, мягкое). `_same_word_form("туберкулема",
  "туберкулеза")` — True, обрезка до шести букв даёт «туберк» обоим. То есть
  подмену болезни глоссарий теперь не создаёт, но оба ОБНАРУЖИТЕЛЯ такой
  подмены по-прежнему слепы. Сводить их в одно нельзя с наскока: `_stems`
  считает ВСЕ баллы проекта.
  **Сторона перевода намеренно оставлена мягкой.** После правки оригинала
  мягкий префикс остаётся единственным основанием всего у 61 требования
  из 1130, и почти все они законны («infiltrate» против «infiltrative»).
  Ужесточение превратило бы их в «нарушения» и отправило бы в платный ремонт.
- **Подбор термина знает про ЯЗЫК, и без правил он строгий, а не свободный**
  (`_LANG_ENDINGS`, `_term_patterns`, `_src_lang`). Раньше отсутствие правил
  означало максимальную нестрогость: класс букв в стем-шаблоне был
  кириллическим, поэтому на латинице совпадал с нулём символов, и находкой
  становился ОБРУБОК («Mycobacterium» → «Mycobacteri», «infiltrate» →
  «infiltra»), а `_same_lexeme` для некириллицы молчала — то есть защита
  от подмены была выключена целиком: «test» ловил «testosterone», «gene» —
  «generalized». Для продажи с любой парой кроме RU→EN это блокер.
  1) **Письменность берётся у КАЖДОГО СЛОВА отдельно** (`_word_script`).
     По всей строке нельзя: «рак in situ» получал бы латинский класс (латинских
     букв больше) и переставал находить «рака in situ», а «вирус HIV» находил
     бы себя внутри «вирус HIVB».
  2) **Склоняется только то, что читается как СЛОВО** (`_WORDISH_RE`: буквы
     одной письменности, между ними допустим дефис или апостроф). Дефис
     обязателен — на нём стоит русская медицинская терминология
     («фиброзно-кавернозный», «клинико-рентгенологический»), и без него
     эти термины перестают склоняться, то есть перестают находиться
     в косвенных падежах. А цифра или скобка внутри («ТУБЕРКУЛЁЗА16»,
     «(CO2)») склонению не подлежит: такие записи требуются ТОЧНО. Без этого
     находка обрывалась на «повторного вдыхания (CO2» без закрывающей скобки.
  3) **Окончания — по языку записи** (`_src_lang` из области: «RU→EN» → «RU»).
     Нет таблицы — стем-поиск НЕ РАБОТАЕТ ВООБЩЕ, остаётся точное совпадение.
     Тот же закон, что у `DOMAIN_RULES` и правил регистра.
  4) **Таблицы минимальны намеренно.** Короткий список — потерянное
     совпадение, длинный — подмена понятия; первое дешевле. Русская проверена
     на 2711 сегментах, английская — на английской стороне того же проекта
     (оттуда убраны «ed»/«ing»: «conditioned → condition» 83 срабатывания;
     «on»/«a»: «plasmon → plasma»). Немецкая, испанская и французская сведены
     к ЧИСЛУ и на данных не проверялись: род и падеж дают «puerto → puerta»,
     «rein → reine», «Rat → Rate».
  5) **Послабление «найденное начинается с записи целиком» — свойство языка**
     (`_WHOLE_WORD_LANGS`). В русском без него не найдётся «туберкулёз»
     в «туберкулёзного» (96 законных совпадений), в английском оно даёт
     «creatin → creating», «derma → dermatologists», «magnet → Magnetic».
  6) **Приписка и замена окончания — разные случаи** (`_LANG_APPEND`, список
     для КАЖДОГО языка, запасной — пустой). Латинское множественное ЗАМЕНЯЕТ
     хвост («bronchus → bronchi»); разреши его припиской — и получишь
     «ARV → ARVI». Запасным вариантом раньше был полный набор окончаний языка,
     и это давало ту же беду в DE/ES/FR: «sal → sala», «rein → reine».
  7) **Цифра в границе слова — только когда термин ею КОНЧАЕТСЯ или
     НАЧИНАЕТСЯ** (`_bound_l`, `_bound_r`). «CD4» не должен ловить «CD40»,
     «Т1» — «Т12», «2HRE» — «12HRE». Глухой запрет отнимал у приказной записи
     законное совпадение: импорт этого учебника приклеивал к словам номера
     страниц («ТУБЕРКУЛЕЗА ОРГАНОВ ДЫХАНИЯ16»). Дефис и апостроф в границу
     не входят никогда: «БЦЖ» обязан находиться в «БЦЖ-вакцина».
  8) **Индекс глоссария видит диакритику** (`_text_keys`). Без этого ключ
     записи «ärzt» не сходился с ключами текста, считанными от «rzte», и
     записи немецкого, французского и испанского не находились бы ВООБЩЕ,
     сколько ни настраивай окончания.
  9) **Поиск и начертание считаются ОДНИМ расчётом** (`_term_forms`). Разойдись
     они — отчёт показывал бы одно, а правка делала другое: `_agreed_form`
     считала начертание в том числе по словам, которые матчер отвергает.
  **Замер на боевых данных** (старый и новый подбор прогнаны по всему
  глоссарию против всех 2711 сегментов из отдельных копий): у ПРИКАЗНЫХ
  записей 1005 совпадений не изменилось, потеряно 0, добавилось 1. По всему
  глоссарию ушло 145 совпадений, и все до одного — на битых записях
  («ТУБЕРКУЛЁЗА16», «клинико-», «бактериовыделением (МБТ+» без скобки).
  Чего не будет никогда: немецкие композиты и умлаут в основе суффиксом
  не берутся. Это предел приёма, а не недоделка.
- **Точное совпадение термина — только по границам слова.** Без этого трёхбуквенные
  записи лезли внутрь чужих слов: «жалобы» → «лоб», «профилактика» → «лак».
- **Предметная область — параметр проекта** (`project["domain"]`, каталог `DOMAINS`).
  Из неё строятся ВСЕ промпты (перевод, проверка терминологии, судья, извлечение
  терминов) и детерминированные правила (`DOMAIN_RULES` в `medical_qa.py`, ключ —
  «область + пара языков»). Хардкодить медицину или RU→EN в новом коде нельзя.
  Нет правил для этой области и пары — проверка МОЛЧИТ, а не срабатывает наугад:
  выдуманная находка хуже отсутствующей. Числа, единицы и соответствие глоссарию
  языконезависимы и работают всегда.
- **Что ещё зашито и мешает продаже — в [BACKLOG.md](BACKLOG.md)** (мультиарендность,
  общий глоссарий, морфология только для русского, бесплатный Google-фолбэк, учёт
  расхода). Правишь что-то из списка — вычёркивай оттуда.
- **Внешние источники (`backend/authorities.py`).** Два вида и разные права:
  **справочник** (`authority_data/*.tsv`) фиксирует пару «оригинал → перевод»;
  **корпус** (PubMed для медицины, Википедия для любого языка) отвечает на другой
  вопрос — «есть ли такой термин в языке» — и потому только НАЛАГАЕТ ВЕТО
  (ноль вхождений = калька) или удерживает на подсказке, но приказа не даёт никогда.
  **У справочника есть уровень (`# tier:` в заголовке файла).** `verified` —
  выверенный отраслевой источник, его совпадение и есть приказ. `auto` —
  краудсорсный (так помечена выгрузка Wikidata: выборочная проверка находит там
  «Анизакидоз → Anisakis», болезнь против рода паразита). Такой приказа в одиночку
  НЕ даёт: он СНИЖАЕТ порог согласия сегментов на один (но не ниже двух), когда
  его подтверждает ещё и корпус целевого языка.
  **Отменить запрет области он не может.** Голоса независимы не полностью:
  модель могла выучить те же ошибки краудсорсного справочника, а корпус
  подтверждает лишь существование строки в языке — «Анизакидоз → Anisakis»
  проходит все три проверки. В медицине, фарме и юриспруденции приказ
  по-прежнему даёт только человек или ВЫВЕРЕННЫЙ справочник.
  Закон тот же, что у `DOMAIN_RULES`:
  нет источника для этой области и пары языков — МОЛЧИМ. `attested() → None`
  означает «не знаю» (сеть, лимит, нечитаемый ответ) и не должно ни одобрять,
  ни блокировать. Корпус спрашивается только про кандидатов, прошедших все
  остальные проверки, с потолком `AUTO_CORPUS_MAX` и троттлингом под лимит
  источника; в разборе `dry_run` он по умолчанию МОЛЧИТ (иначе открытие
  проекта — минута ожидания), а ответ помечается `corpusPending`.
- **Второй клик (`kind: "apply_terms"`).** Одобряет пачку терминов, затем чинит
  ими сегменты. Состав считается ПОСЛЕ одобрения и берётся из `glossary_impact`
  (только разошедшиеся с утверждёнными терминами), а не из «всех, где есть
  находки»: человек нажал «применить термины», а не «перебрать проект».
  Остановка проверяется ДО записи глоссария — он меняется одним куском.
- **Сверка терминов моделью (`kind: "termaudit"`)** — штатный шаг конвейера
  между проверкой терминов и ремонтом. Спрашивает про ВСЕ приказные термины
  сегмента, а не только про спорные: соседи + список терминов → вердикт
  по каждому, один вызов на сегмент.
  **Зачем отдельный шаг, если есть детерминированная проверка.** Та знает
  морфологию ОДНОГО языка и знает её грубо: «туберкулёз лёгких» обратный
  перевод возвращает как «лёгочный туберкулёз», и по словам это потеря.
  Модель отвечает на тот же вопрос без всякой морфологии и на любом языке —
  ради этого шаг и заведён. Это и есть ответ на «как быть с языками, для
  которых таблицы окончаний нет»: писать морфологию под каждый язык не нужно,
  нужен платный вопрос модели. Цена измерена по боевым прогонам: полный
  конвейер стоит $0.0056 за сегмент, лишняя сверка — $0.001–0.002, то есть
  $3–5 на книгу в 2711 сегментов.
  **Детерминированный подбор при этом остаётся** и остаётся первым ситом:
  он бесплатен, повторяем и отвечает мгновенно, поэтому по нему считаются
  состав прогона и экран «Анализ». Модель на каждое открытие экрана
  не позовёшь. Тот же приём, что у termcheck и сверки смысла: дешёвая
  проверка НОМИНИРУЕТ, модель РЕШАЕТ.
  Вердикт кэшируется на сегменте (`seg["termContext"]`) по хешу перевода
  и версии вопросов (`TERM_CONTEXT_VERSION`) — как back-check и termcheck.
  Промпт один на оба режима (разбор спора и сверка всего), поэтому вердикт,
  полученный шагом, закрывает и спор. Меняешь промпт — поднимай версию.
  **Состав шага считает сервер и берёт его из ГОТОВОГО прохода**
  (`glossary_impact` → `termSegments`, тем же расчётом и теми же `hits`, что
  `caseSegments`). Второй проход `_verified_hits` по проекту стоит 40 секунд
  единственного воркера, а разбор пересчитывается на каждую смену модели
  и галочки — ровно та беда, из-за которой туда же ходит и ремонт.
  Список — ускорение, а не источник правды: без него разбор считает сам,
  меняется только скорость.
  **Вердикт помнит ОХВАТ** (`termContext.all_terms`). Разбор спора спрашивает
  только про спорные термины, сверка — про все. Без этой отметки вердикт
  разбора закрывал сегмент для сверки навсегда: на боевом проекте так осталось
  бы не сверено 89 приказных терминов в 61 сегменте.
  **Дедупликации по паре «оригинал+перевод» здесь НЕТ намеренно**, и это
  сказано вслух, потому что контракт прогонов её требует: ответ арбитра зависит
  от СОСЕДЕЙ, а не только от пары. На боевом проекте среди 713 берущихся
  сегментов 711 уникальных пар — вся экономия составила бы два вызова
  из семисот. Параллельность при этом есть (`_run_parallel`): вызов модели —
  это ожидание сети.
  **Смета главной кнопки обязана знать про шаг** (`fullEst` в `tab_editor.jsx`,
  сторожится тестом по `FULL_RUN_STEPS`). Шаг, у которого есть работа, но нет
  цены, — худший вид молчания: человек видит одну сумму, списывается другая,
  и она же уходит в историю расхода как `est_cost`, по которому калибруется
  поправка `estRatio`.
  **Состав обеих кнопок — из серверного разбора.** Браузер приказные термины
  сегмента не считает и считать не должен: замер показал 713 против 2711,
  разница в 3.8 раза под соседними кнопками.
  **Шаг идёт ПЕРЕД ремонтом, и это несущее свойство**: «передан верно» снимает
  претензию (`_repair_findings` пропускает такой `term_lost`), а «передан
  неверно» ремонту не отдаётся и уходит человеку в `/analysis` — это вопрос
  к ЗАПИСИ глоссария, а не к строке.
- **Составной прогон (`kind: "full"`).** Одна кнопка на весь конвейер: порция
  проходит `FULL_RUN_STEPS` подряд — перевод → back-check → термины → ремонт →
  Medical QA. **Порядок задаёт сервер, а не клиент** (клиент выбирает только состав):
  терминологию собирает та из двух проверок, что отработала второй, ремонту нужны
  находки обеих. **Medical QA идёт ПОСЛЕДНЕЙ**, и это не косметика: находок её
  не читает никто (`_repair_findings` смотрит back-check, termcheck и глоссарий,
  а числа и отрицания считает сам back-check через `medical_qa.run_backcheck`),
  зато стоя перед ремонтом она описывала текст, который через шаг переписывали, —
  и оставалась устаревшей, так что следующий прогон забирал те же сегменты снова. У каждого шага СВОЯ модель (`FULL_STEP_MODEL`); незаполненная
  означает «возьми свою по умолчанию», а НЕ модель переводчика — иначе back-check
  идёт той же моделью, что переводила, и перестаёт быть независимой проверкой,
  на которой стоит автоодобрение. Шаг без ключа или модуля не роняет прогон
  (`blocked` → счётчик `step_skips`), но порция, где не отработал НИ ОДИН шаг,
  падает. Внутри перевод идёт с `force=False`, проверки — со `skip_cached=True`.
- **`engine: "auto"` у `/batch`** — движок выбирается посегментно по `risk`
  (`low_engine`, по умолчанию `gpt`). Без него составная кнопка брала бы половину
  сегментов: отбор для `gpt` отбрасывает короткие, для `google` — длинные.
- **`_replace_target` — единственное место, где машина меняет текст сегмента.**
  Правило одно на всех (перевод, подстановка из TM, рассылка повторов): если
  перевод заверял человек, прежний текст уходит в `prevTarget`, статус
  становится `review`, отметка `confirmedBy` снимается — она относилась к тексту,
  которого больше нет. Пакетные прогоны (перевод, ремонт) подтверждённые
  вообще не берут без явного `include_confirmed`.
- **Точное совпадение с TM подставляется только от `quality: "verified"`**
  (`_tm_trusted`) и ставит `translated`, а НЕ `confirmed`: одно подтверждение
  человека на одной строке не заверяет все будущие строки с тем же исходником.
  Память переводов была единственным местом, где чужая ошибка попадала в перевод
  мимо глоссария и мимо всех проверок.
- **Колонки «TM%» больше нет, и нечёткого поиска по памяти тоже.** `seg["tmScore"]`
  писался единожды НУЛЁМ при импорте и не обновлялся ничем: на боевом проекте
  все 2670 сегментов имели `tm: None, tmScore: 0`, то есть чип красил красным
  нулём каждый сегмент каждого проекта всегда. Раскраска в `data.js` работала
  только по `window.SEED` — демо-заглушке макета. Постоянный ложный показатель
  хуже отсутствующего: по нему делают выводы о памяти переводов, которых он
  не подтверждает. Колонка в таблице теперь называется «Проверки» и несёт
  ровно то, что там и лежало: ремонт, находки по терминам, балл back-check.
  Настоящие совпадения TM видны в карточке сегмента (вкладка «TM») — они
  берутся из `store.tm`, а не из `tmScore`. Вернётся нечёткий поиск — будет
  чем заполнить чип; до тех пор его отсутствие честнее его показаний.
  Поле `tmScore` больше не пишется и при импорте: с экрана убрать мало, в
  `state.json` выдуманный ноль остался бы, и следующий, кто его найдёт,
  поверит. Сама подстановка (`_tm_trusted`, `route: EXACT_TM`) как работала,
  так и работает — на боевом проекте она сработала 1 раз на 106 записей
  памяти. Нечёткого поиска по TM нет вовсе, и это записано в [BACKLOG.md](BACKLOG.md).
- **`tests/test_routes.py` сторожит таблицу маршрутов.** Хелпер, вставленный
  МЕЖДУ декоратором и функцией, забирает её маршрут себе: `@app.get(...)`
  достался `_verified_hits`, и `/glossary-impact` начал отвечать 422 на любой
  запрос. Логика при этом исправна, поэтому молчали все шестнадцать наборов
  и рендер фронтенда — на экране просто пропала карточка. Ловится двумя
  дешёвыми правилами: приватная функция (`_имя`) маршрутом быть не может,
  и обработчик обязан объявлять параметры своего пути. Сверки «имя похоже
  на путь» там нет намеренно — `save_term` на `/api/glossary` законен.
- **«Пересчитать» у соответствия глоссарию идёт с `refresh=true` и отвечает
  словами.** Отчёт кэширован по отпечатку проекта, поэтому без `refresh`
  нажатие возвращало посчитанное раньше — то есть не делало ничего. А расчёт
  идёт доли секунды, и молчаливое нажатие неотличимо от сломанной кнопки:
  теперь называется «было N, стало M», и «столько же» — тоже ответ.
- **Карточка «Соответствие глоссарию» не прячется при нуле.** Она рисовалась
  только при непустом `impact.terms`, и вместе с ней исчезала «Пересчитать» —
  единственный способ убедиться, что ноль настоящий, а не остался с прошлого
  расчёта. Ноль там штатный: понижение записи сверкой смысла убирает её
  из требований, и расхождений может не остаться совсем. Тот же закон, что
  у корзин `/analysis` ниже: пропавшее с экрана выглядит благополучнее, чем
  есть. Проверяется в `tests/test_editor_render.js` — заглушка отдаёт пустой
  отчёт.
- **`/api/projects/{pid}/analysis`** — итог по проекту одним экраном. Корзины
  обязаны быть ИСЧЕРПЫВАЮЩИМИ: сегмент, не попавший ни в одну, исчезает с экрана,
  и картина выглядит благополучнее, чем есть. Кэш по отпечатку, куда входят и
  сами оценки (балл back-check, число находок), а не только хеши текста.
  **Корзины разбираются по КОДУ причины, а не по подстроке русской фразы**
  (`CLEAN_*`, `CLEAN_UNCHECKED`). Сравнение вида `"не делался" in why` молча
  ломается от правки формулировки: сегмент уезжает в чужую корзину, и на
  экране это выглядит как правда.
  **Переписанный ремонтом сегмент в «оценку ниже порога» НЕ идёт**
  (`CLEAN_REPAIRED`). `_machine_clean` отвечает на вопрос «можно ли учить этим
  глоссарий», а корзина подписана «оценка ниже порога» — это разные вопросы.
  У такого сегмента back-check прошёл и termcheck чист; отказ он получил
  только за то, что систему нельзя пускать заверять собственную правку.
  На боевом проекте это 306 сегментов из 511, то есть корзина на 60% состояла
  из благополучных строк и звала человека разбираться там, где разбираться
  не в чем.
  **Глоссарий `_machine_clean` не смотрит ВООБЩЕ** — ни `_gloss_misses`,
  ни `_verified_hits`. Значит «Проверено начисто» не означает «глоссарий
  соблюдён», и подписывать эту строку так нельзя: сегмент с нарушенным
  приказным термином и чистыми проверками попадает и в «начисто», и в
  «Расходятся с глоссарием» одновременно.
  **Исчерпаемость держится на `repaired_set`, а не на совпадении предикатов.**
  Условие выброса и условие попадания в «Исправила машина» сегодня совпадают
  буква в букву, но лежат в тысяче строк друг от друга и однажды разойдутся.
  Разойдись они при сравнении по множеству — сегмент окажется в «оценке ниже
  порога»: видно и слегка неверно. Разойдись при повторе условия — исчезнет
  с экрана совсем, а это худшая из здешних ошибок.
  **Балл ниже порога у КОРОТКОГО оригинала — своя причина** (`CLEAN_LEX_BLIND`),
  а не «оценка ниже порога». Мерить было нечем (см. `_judge_zone`), и пока
  судья не ответил, число ничего не значит; на боевом проекте таких 30 из 36
  оставшихся. Без этой строки они лежали бы ровно там, откуда только что
  вынесли 306 починенных, и по той же причине: система знает, что цифра
  пустая, а человеку показывает её как приговор. Причина ЛОКАЛЬНАЯ, для
  корзины: `_machine_clean` по-прежнему отказывает такому сегменту в праве
  учить глоссарий, и это правда — балл действительно ниже порога.
- **Прогоны идут на сервере (`_JOBS`, `/api/projects/{pid}/jobs`).** Браузер только
  ставит задачу и опрашивает статус: закрытая вкладка больше не обрывает работу.
  Рабочий поток ОДИН и очередь одна — воркер uvicorn один, `STATE` общий, два
  параллельных прогона дрались бы за `state.json`. Задачи живут в памяти процесса:
  рестарт сервиса их теряет (сделанные сегменты сохранены). Остановка мягкая —
  текущая порция досчитывается. Порция, где не прошло НИЧЕГО, роняет прогон
  в `error`: пакетные эндпоинты глотают ошибки посегментно, и без этого мёртвый
  ключ выглядел бы как «выполнено».
- **Балл back-check не отменяет правку, ПОЧИСТИВШУЮ ТЕРМИНЫ.** Балл — доля
  основ ОРИГИНАЛА, вернувшихся через обратный перевод (`_content_recall`),
  поэтому он вознаграждает КАЛЬКУ: «Erect solar rays» возвращается как «прямые
  солнечные лучи» слово в слово и набирает почти единицу, а верное «direct
  sunlight» возвращается синонимом и балл роняет. Про сам back-check это здесь
  сказано с самого начала («на кальке всегда отвечает „да“»), но его баллом
  меряли правку termcheck — проверки, заведённой РОВНО против кальки.
  На боевом учебнике так выброшены 111 верных правок из 216 отменённых:
  «medicine physicians» → «pulmonologists», «sanguiferous bed» → «bloodstream»,
  «chronic active (CAH) diseases» → «chronic diseases», «an infected animal» →
  «the patient». Медиана падения 24 пункта, и это НЕ эффект коротких сегментов:
  медиана длины 23 содержательных слова, `lexically_blind` у 2 из 111.
  Ослабление узкое, границы две:
  1) улучшение считается по БЕСПЛАТНЫМ объективным счётчикам (серьёзные находки
     termcheck, нарушенные приказные термины), а не по мнению модели о своей
     работе;
  2) **жёсткая находка на новом тексте остаётся вето при любом улучшении
     терминологии** (`backcheck.hard`, `BACKCHECK_HARD_TYPES` — числа, единицы,
     отрицание, подмена стороны): она не зависит ни от морфологии, ни от
     буквализма, а размен числа на термин — не работа.
  Обоснование то же, каким обоснован `only_minor`: у захода должна быть
  измеримая цель, а на правке кальки балл меряет не то. Решение, принятое
  вопреки баллу, пишется в `repair.notes` — иначе принятую правку с упавшим
  баллом нечем объяснить. Флаг `hard` кладётся в запись back-check и читается
  только тем, кто её сам и написал (перепроверка внутри ремонта), поэтому
  у старых записей его отсутствие ни во что не превращается.
- **Судья с ОБЕИХ сторон либо ни с одной** (`judge_after` в `_run_segment_repair`).
  Прежний балл мог сложиться с участием судьи (`JUDGE_CAP` опускает,
  `JUDGE_FLOOR_NONE` поднимает), а перепроверка после правки идёт с `use_judge`
  из прогона — тумблер «Судья» выключен по умолчанию. Тогда сравнивались два
  числа разной природы: вердикт против сырого измерения. На боевых данных так
  вышло у 66 отмен из 176, и падение у них медианно 25 пунктов против 12
  у остальных. Судья зовётся там, где он участвовал в прежней оценке, — лишний
  вызов только на таких сегментах.
- **Сбой перепроверки откатывает правку, но заход НЕ засчитывает.** Ветка
  «перепроверка терминов не выполнилась» — про оборванный вызов, а не про
  качество правки. Откат правильный (система не заверяет сама себя), а вот
  `repair.source_hash` в этом случае не пишется: клеймо `tried` закрыло бы
  сегмент от ремонта навсегда из-за чужой сетевой ошибки. На боевом проекте так
  потеряны 5 верных правок (#645: «accidental» → «casual», балл не падал вовсе).
  **Считается это, только когда сбой — ЕДИНСТВЕННАЯ причина** (`len(why) == 1`):
  стоит рядом претензия по существу (нарушен приказный термин, замечаний стало
  больше) — правку отвергли по делу, вердикт вынесен, и повторный заход даст
  то же самое за те же деньги. Иначе одна оборванная перепроверка отпирала бы
  обратно любой сегмент, отвергнутый законно. На экране такие сегменты идут
  своей группой (`retryable` → `rpGroupKey` = `failed`, отмечена по умолчанию):
  «текст менялся» там неправда — текст как раз не менялся.
  **Заклеймлённые прежним кодом разжимает миграция** в `_apply_migrations`
  (на боевом проекте 9 сегментов). Сверяется она с ПОЛНЫМ совпадением строки
  причины — константа `REPAIR_RECHECK_FAILED`, ею же пишет и сам ремонт:
  в данных лежит этот литерал, и переформулировать его задним числом нельзя.
  Причина отказа сохраняется, теряется только запись о попытке — ровно то,
  чего прежний код не должен был писать; миграция идемпотентна. Хешей в ней
  нет намеренно: `_apply_migrations` зовётся при импорте (`STATE = load_state()`)
  задолго до того, как определён `_text_hash`, — по той же причине, по которой
  отдельным поздним проходом идёт `_migrate_term_queue`. И сама константа
  объявлена ВЫШЕ миграции: объявленная по соседству с `TERMCHECK_ACTIONABLE`,
  она роняла импорт с NameError.
- **Наследство прежнего правила разбирается вручную и без вызова модели**
  (`_repair_score_vetoed`, `POST /api/segments/{pid}/{sid}/repair/accept`).
  Записи, сделанные до правки, никуда не делись, и отменённый текст лежит
  в `repair.candidate` — написанный и оплаченный. Предикат узкий: причина
  отмены РОВНО одна и это балл (`;` в строке означает, что были и другие,
  законные), термины при этом стали чище, а кандидат относится к НЫНЕШНЕМУ
  тексту (`_repair_tried`) — иначе перевод правили после отмены и подстановка
  выбросила бы чужую работу, ровно как в `_revert_repairs`. Сравнение по строке
  причины здесь законно (в отличие от корзин `/analysis`, где заведены `CLEAN_*`):
  строку писал этот же файл, она лежит в данных прошлых прогонов, и
  переформулировать её задним числом нельзя.
  **Третья команда в системе, меняющая текст БЕЗ вызова модели** — после
  `/glossary/revert-repairs` и `/term-case`, и по той же причине: она ничего
  не сочиняет. **Пачкой это делает `POST /api/projects/{pid}/repair/accept-batch`**
  (кнопка «Принять все» в строке `/analysis`), и живёт она по правилам массовых
  команд: `dry_run` по умолчанию, заверенное человеком не трогается без
  `include_confirmed` и названо числом, прежнее состояние сегментов целиком
  уходит файлом в `data/backups/` и возвращается
  `/repair/accept/{stamp}/undo`. Оговорку надо понимать и она сказана
  в подтверждении: проверки прежнего текста после подстановки устаревают сами,
  а нового ещё нет ни у кого — пачка переводит сегменты в «никем не проверено»
  до ближайшего прогона. **Метка отката разводится суффиксом при занятости**:
  две пачки подряд укладываются в одну секунду, и вторая молча затирала бы
  копию первой — бэкап, который можно затереть, не бэкап. Откат возвращает
  ТОЛЬКО те сегменты, где сейчас стоит именно принятый кандидат; правленые
  после названы в `changedSince` — тот же закон, что у `_repair_tried`
  в `_revert_repairs`. Применение одиночной и пакетной команды идёт ОДНОЙ
  веткой (`_apply_repair_candidate`): разойдись они — «принять» и «принять все»
  оставляли бы сегмент в разных состояниях.
  Признак для кнопки считает СЕРВЕР (`repair.acceptable`
  в `_segment_for_client`), как и `tried`: повтори правило браузер — кнопка
  предлагалась бы там, где эндпоинт отвечает 400. Своя строка в `/analysis` —
  `human.revertedByScore`, ПОДМНОЖЕСТВО `reverted`: отдельной корзиной
  исчерпаемость держалась бы на совпадении двух предикатов в разных концах
  файла.
- **Отложенная галочками работа видна в СВЁРНУТОЙ строке ремонта** (`rpWaiting`
  в подсказке строки). Группы «уже чинилось» и «правка была откачена» сняты
  по умолчанию и живут в раскрытой части — на боевом проекте так молча стояли
  510 сегментов с находками, а состав шага показывал «—», и понять почему было
  неоткуда. Тот же закон, что у `impact["futile"]`: расходиться с находками они
  не перестали, и молчать об этом нельзя. Число считается по тем же `rpGroups`,
  что и таблица в раскрытой части, — второй расчёт разошёлся бы с ней.
- **Пустой заход ремонта не оплачивается (`_repair_futile`).** `_repair_tried`
  смотрит только на текст, и этого мало: глоссарий меняется, и по НОВОЙ
  претензии зайти на тот же текст осмысленно — ради этого `apply_terms` и ходит
  со `retry=True`. Но когда и текст тот же, и СПИСОК ПРЕТЕНЗИЙ тот же, модель
  получит тот же промпт и вернёт тот же ответ, а оценка отвергнет его так же.
  На боевых данных это были все 57 оставшихся расхождений: каждое нажатие
  «Применить» стоило денег и не меняло ничего, список оставался прежним —
  работа выглядела нескончаемой. Такие сегменты из состава прогона убраны,
  но из отчёта о соответствии НЕ спрятаны (`impact["futile"]`, строка «ремонт
  уже не берёт»): расходиться с глоссарием они не перестали, просто чинит их
  теперь человек или другая модель. Число считается в `glossary_impact`, чтобы
  карточка и состав прогона брали его из одного расчёта.
- **Автоматический ремонт (`seg["repair"]`).** Чинит по конкретным находкам, после чего
  перепроверяет ТЕМИ ЖЕ проверками и оставляет новый текст, только если оценка не упала.
  Иначе — откат вместе с восстановлением прежних проверок. Статус после ремонта `review`,
  не `confirmed`: автоправка не заверяет сама себя. Один заход на один текст
  (`repair.source_hash`), производный `tried` — как `stale`.
  **Находки termcheck уровня `minor` ремонт берёт наравне с `critical`/`major`**
  (`TERMCHECK_ACTIONABLE`). Раньше их не брал никто: ремонт чинил только две
  верхние ступени, а `_machine_clean` всё равно объявлял сегмент нечистым —
  168 сегментов боевого проекта висели между двумя политиками и не двигались
  ни в какую сторону. Находки при этом содержательные: «EPT → EPTB»,
  «Amount → Number», «extensive drug resistance → extensively drug-resistant».
  Один и тот же кортеж читают ремонт, корзина споров в `/analysis` и
  `_note_term_disputes` — разойдись они, ремонт ходил бы за находкой, которой
  экран не показывает.
  **Заход, где кроме мелочи ничего не было, сверяется ПОИМЕННО** (`only_minor`,
  `minor_targets`): успех — ушла хотя бы одна из ТЕХ находок, ради которых
  зашли. Только у такого захода нет ни одной другой измеримой цели: балл
  back-check не пересчитывается, нарушать глоссарию нечего, серьёзных находок
  и до правки не было — «не стало хуже» засчитало бы успехом любой
  переписанный текст.
  **Считать при этом по количеству нельзя.** termcheck на переписанном тексте
  почти всегда добавляет свою придирку, и правило «мелочи должно убавиться»
  откатывало бы верное «EPT → EPTB» по счёту «1 → 1», а сегмент клеймило бы
  `tried` — то есть чинить его не пришли бы уже никогда. Рост ОБЩЕГО числа
  мелочи откатывает и при снятом заказе: две новые придирки взамен одной
  старой — не работа.
  **Смешанный заход мелочью не меряется вовсе.** У него есть свои счётчики
  (балл, серьёзные находки, нарушенные приказные термины), а откатывать
  верную подстановку термина из-за побочного `minor` значит отнять
  автоматизацию там, где она работала.
  **Карусели тут нет и не было**: ветка применения пишет `repair.source_hash`
  по НОВОМУ тексту, поэтому `_repair_tried` закрывает сегмент сразу после
  принятой правки, а `_repair_futile` — после откачённой. Обратная сторона
  та же: откачённый по мелочи сегмент закрыт, и дальше это работа человека
  или другой модели.
  **Забракованный ПОДСТАВЛЕННЫЙ термин откатывает при любой тяжести.**
  За слово, которое вписали мы, отвечаем мы целиком: оставь там только
  critical/major — и мелкое замечание на свежеподставленном термине правку
  не отменит, зато следующий прогон сделает из него повод для ремонта, ремонт
  полезет менять утверждённый термин, `gloss` вырастет и правку откатят.
  Платный вызов с заранее известным исходом.
  **Соответствие глоссарию — такая же находка ремонта** (`_gloss_misses`, `kind: "gloss"`),
  считается тем же расчётом и по тем же `verified`, что и `/glossary-impact`: разойдись
  они в определении нарушения — переписывали бы сегмент друг за другом по кругу.
  Все проверенные записи сегмента уходят в промпт ремонта целиком, даже нетронутые:
  без этого модель, починив одно, свободно выбивала утверждённый термин в другом месте.
  Число нарушенных терминов входит в `_repair_scores` и сверяется ВСЕГДА, а не только
  когда чинили из-за глоссария, — эта оценка не стоит ни одного вызова модели.
  **Откат возвращает проверки прежнего текста, а НЕ оставляет свежие.** Если
  прежней проверки не было, свежая снимается совсем: раньше `seg[k] = seg.pop(k)`
  выковыривал ключ и клал обратно, и на восстановленном тексте оставалась
  проверка ОТВЕРГНУТОГО варианта — находка про слова, которых в сегменте нет.
  Случай штатный: расхождение с глоссарием заказывает termcheck сегменту,
  который termcheck до этого ни разу не видел.
  **Текст сегмента сверяется с записью о решении на выходе** (`_repair_desync`).
  Расходиться им нечем — и откат, и применение кладут текст сами, следующей
  строкой, — но в данных прогона 22.08 нашлись 34 сегмента, где запись описывает
  один текст, а лежит другой; воспроизвести на нынешнем коде не удалось.
  Проверка не чинит, а называет: сегмент и оба текста в журнал, число —
  в счётчик прогона `desync`. По этим записям считается «откачено N» и решается,
  заходить ли на сегмент второй раз, поэтому молчать о расхождении нельзя.
- **Внутри порции вызовы идут параллельно** (`_run_parallel`, `RUN_WORKERS`, по умолчанию 6).
  Вызов модели — это ожидание сети, а не процессора. Мутации STATE применяет основной
  поток: рабочие функции возвращают результат, а не пишут в общие структуры. Всё, что
  пишет в общее (`_queue_term`), обязано брать лок. Поднимать RUN_WORKERS выше лимитов
  аккаунта бессмысленно — начнутся 429 и повторы.
- **Во время прогона клиент забирает только обработанные сегменты**
  (`POST /api/projects/{pid}/segments/fetch` + `job.recent`). Полный проект на 2670
  сегментов весит 5 МБ; тянуть его каждые несколько секунд — мегабайты трафика
  и подвисающая таблица.
  **Поэтому по окончании прогона проект подтягивается ЦЕЛИКОМ, и подстановку
  нельзя отменять по `dead`.** Порция обновляется по `job.recent`, а вкладка,
  ушедшая в фон, душится браузером до одного опроса в минуту и пропускает
  порции целиком — на боевом проекте так осталось 25 сегментов из 41 со
  статусом «новый», хотя на сервере их давно перевели. Полная подстановка
  и есть страховка от этого, но стояла она под `if (!dead …)`, а `dead`
  взводит cleanup эффекта, который запускает `setJob(null)` СТРОКОЙ ВЫШЕ:
  условие отменяло подстановку не иногда, а ВСЕГДА. Отчёт о прогоне при этом
  показывался (он идёт до `await`), поэтому со стороны всё выглядело
  исправным. Отметки две и путать их нельзя: `reportedJob` — «отчитались»
  (один раз), `lastJobId` — «результат ещё не забрали» (снимается только
  после удавшейся подстановки, иначе оборванная сеть оставляет таблицу
  устаревшей навсегда). Ещё три правила вокруг них:
  1) **подстановка идёт РОВНО ОДНА за раз** (`pullProject`, замок `pullBusy`).
     `setJob(null)` пересоздаёт эффект опроса, и новый экземпляр немедленно
     делает свой `tick` и находит тот же завершённый прогон: без замка конец
     каждого прогона стоил бы двух-трёх ответов по пять мегабайт подряд на
     единственном воркере. Замок заодно отвечает и на вопрос «какой ответ
     новее»: второго запроса просто нет, поэтому отставший снимок не может
     лечь поверх свежего и стереть с экрана только что поставленную отметку
     «подтвердил человек»;
  2) **у попыток есть потолок** (`PULL_TRIES`). Без него вкладка раз в 15 с
     бесконечно долбит самый тяжёлый эндпоинт — это самообстрел, а воркер
     ОДИН. Исчерпав попытки, вкладка говорит вслух «обновите страницу»:
     молча оставленные допрогонные статусы — ровно тот баг, что здесь чинится;
  3) **прогон опознаётся ТРОЙКОЙ «номер + проект + время создания»**, как и
     снимок состава (`runStepRows`). Номера задач живут в памяти процесса
     и после рестарта сервиса начинаются с единицы заново: по голому номеру
     отчёт о новом прогоне №3 считался бы уже сделанным и пропал бы молча —
     вместе с ценой, числом ошибок и обновлением карточек.
- **Устаревшую копию проекта браузер ловит ДВУМЯ сверками, и вторая — про
  статусы** (`projectStatus` у `/run-plan`, `_status_counts`). Числом сегментов
  ловятся только ДОБАВЛЕННЫЕ мимо вкладки (разбор картинок с соседнего экрана);
  прогон же ничего не добавляет — он меняет статусы, и число сходится.
  Тогда в одном окне стоят два ответа на один вопрос: строка «Перевод» говорит
  «—» (её считает сервер), а фильтр — «Новые 25» (его считает браузер по своей
  копии). Три правила:
  1) **нормализация «нет статуса = new» обязана совпадать на сервере
     (`_status_counts`) и в браузере (`statusCountsOf`)** — разойдись они,
     сверка находила бы расхождение там, где его нет, и тянула бы пять
     мегабайт на каждый разбор состава;
  2) **считается ВЕСЬ проект, а не выбранные сегменты**: браузер сверяет свою
     копию целиком, и разбивка по выборке нашла бы расхождение на пустом месте;
  3) **своя правка, ещё не доехавшая до сервера, расхождением не считается**
     (`API.segEdits`, счётчик запросов под `/segments/`). Правка применяется
     в браузере сразу, а на сервер уходит отдельным запросом — разбор,
     посланный между этими событиями, честно вернёт статусы ДО неё, и без
     этой оговорки каждое нажатие «Подтвердить» тянуло бы весь проект заново.
     Отпечаток строкой «начато:закончено», а не флагом «занято»: правка,
     успевшая и начаться, и закончиться за время разбора, флагом не ловится.
     **Не доехавшая правка (`failed`) выключает сверку насовсем**: в браузере
     лежит текст, которого сервер не знает, и подстановка выбросила бы его
     молча — вместе с набранным человеком переводом. Несохранённая работа
     дороже автоматической синхронизации.
     Счёт идёт по префиксу пути `/segments/`: там лежат ВСЕ команды, меняющие
     ОДИН сегмент (перевод, подтверждение, откат, правка, ремонт, рассылка
     повторов). Вернёшь прямой вызов пакетного `/projects/{pid}/batch` из
     браузера — считаться он не будет, и сверка потянет проект впустую;
  4) **пока результат прогона не забран, сверка молчит** (`settled`), и между
     сверками есть пауза (`DRIFT_PAUSE_MS`). Без первого она сравнивала бы
     ДОПРОГОННУЮ копию с послепрогонным ответом и тянула бы те же пять
     мегабайт второй раз, показывая тост про аварию после каждого штатного
     прогона. Без второй — пока прогон идёт в СОСЕДНЕЙ вкладке (о нём эта
     узнаёт не сразу: опрос в простое раз в 15 с), сверка гоняла бы
     «разбор → пять мегабайт → разбор» по кругу.
- **Повторы исходника переиспользуются ПО ВСЕМУ проекту, а не только внутри
  порции.** Один и тот же заголовок в сегментах 12 и 500 попадал в разные порции
  и оплачивался дважды. Донором становится не первый по документу, а лучший:
  заверенный человеком сильнее машинного, а `failed` донором не бывает вовсе —
  копировать брак в близнецов значит размножить его. Память переводов идёт
  ПЕРЕД повтором: её записи подтверждал человек. Копия наследует провайдера
  донора (писать «tm» на тексте соседнего сегмента — врать о происхождении)
  и получает `route: DUPLICATE`, поэтому донором для глоссария не становится.
- **Medical QA помнит, к какому тексту относится результат** (`qa_result.target_hash`,
  производный `stale` — как у back-check и termcheck). Без этого она одна брала
  в работу ВСЕ переведённые сегменты, и составной прогон всегда показывал полный
  проект, сколько бы раз его ни запускали. Отметка ставится ТОЛЬКО при полной
  проверке: без обратного перевода часть находок не считается, и кэшировать
  такой результат значит закрыть сегмент от нормальной проверки навсегда.
- **Своей модели у Medical QA нет, но вызов есть.** Правила детерминированные,
  платный вызов нужен ровно один — обратный перевод, и только там, где готового
  от back-check не осталось. Модель этого вызова — `bc_model` (по умолчанию
  `BACKCHECK_DEFAULT_MODEL`), а НЕ модель перевода: без явного указания сюда
  подставлялся `DEFAULT_OPENAI_MODEL`, и та же самая работа стоила в разы дороже
  моделью, которую для обратного перевода никто не выбирал.
- **Статус проверка может только поднять до `review`, но не понизить.**
  `confirmed` неприкосновенен (проверка не изменила ни буквы текста), `review`
  тоже: его ставят те, кто ПЕРЕПИСАЛ текст, и значит он про «на текст смотрела
  машина, посмотри человек». Medical QA на этот вопрос не отвечает, а понижая
  `review` до `qa`, уводила починенные сегменты из зоны внимания.
- **Хеш сравнивают так же, как записывают — по ОБРЕЗАННОМУ тексту.**
  `_check_stale`, `_backcheck_cached`, `_termcheck_cached`, `_repair_findings`
  (там сравниваются хеши back-check и termcheck; `repair.source_hash` — сырой,
  его так же сырым и пишут): writers пишут хеш
  `target.strip()`, и сравнение с необрезанным перезапускало платную проверку
  на каждом переводе с висящим пробелом, пока интерфейс показывал её свежей.
- **Фактический расход снимается с ответа модели, а не пересчитывается нами**
  (`_note_usage` на каждом вызове: перевод, back-check, termcheck, судья,
  извлечение терминов, ремонт, эмбеддинги). Смета до прогона обязана ошибаться —
  сколько модель ответит, знает только она; беда была в том, что факт нигде
  не записывался и поправить смету было не по чему. Так и жила ошибка termcheck:
  смета клала 450 выходных токенов на сегмент, а ответ занимал 37.
  Итог прогона `_usage_end` пишет в `STATE["runCosts"]` (последние
  `RUN_COST_HISTORY`) **вместе со сметой** (`params["est_cost"]`, её присылает
  тот же фронтенд, что показал её человеку): врозь эти два числа не сравниваются,
  а ради сравнения всё и затевалось. `/api/usage` отдаёт факт, историю и
  поправку `estRatio`. Три правила: цена неизвестна — это `None`, а не ноль
  (`unpriced` считается отдельно; неизвестное, посчитанное нулём, показывает
  расход меньше настоящего); скидка на кэшированный вход не применяется, её
  цены в каталоге нет, поэтому цифра завышена ровно на неё и рядом лежит
  `cached_in`; учёт целиком в `try` — перевод, не состоявшийся из-за
  бухгалтерии, обошёлся бы дороже неточной сметы. Счётчик прогона —
  переменная процесса (`_USAGE_SINK`), а не `contextvars`: прогон в системе
  один, а `_run_parallel` раздаёт работу в `ThreadPoolExecutor`, который
  контекст не наследует.
- **Экономия вызовов — часть контракта прогонов.** Повторы внутри порции (одинаковый
  исходник в переводе, одинаковая пара оригинал+перевод в back-check и termcheck)
  считаются один раз; судья не вызывается при жёсткой находке (его вердикт всё равно
  ничего не изменит); эмбеддинги считаются лениво и кэшируются; Medical QA берёт готовый
  обратный перевод из `backcheck`; termcheck не тратит вызов на сегменты без слов.
  Добавляя новый прогон, добавляй и дедупликацию — иначе пакет на 2000 сегментов
  оплачивает одни и те же заголовки десятки раз.
- **Проверка терминологии (`seg["termcheck"]`) — не back-check.** Back-check спрашивает
  «пережил ли смысл обратный перевод» и на кальке всегда отвечает «да»: «rear cyclitis»
  дословно возвращается как «задний циклит». Termcheck смотрит только на перевод и
  спрашивает «нормальный ли это термин целевого языка». Кэш по `target_hash` + РАНГУ
  модели, производный `stale` — как у back-check.
- **Ранг модели (`backend/model_ranks.json`, `model_rank`).** Нужен для одного
  решения: вправе ли проверка одной моделью перезаписать готовую проверку другой.
  `_termcheck_cached` признаёт действительным вердикт модели НЕ СЛАБЕЕ запрошенной —
  иначе достаточно сменить модель в списке, чтобы тысяча проверенных Sol сегментов
  ушла на перепроверку Terra, оплаченную и худшую. Обратное направление разрешено:
  усилить проверку можно всегда. Ранг лежит ФАЙЛОМ и перечитывается при изменении:
  список моделей меняется чаще, чем выходят релизы, и правка ранга не должна
  требовать деплоя; копия в `data/model_ranks.json` сильнее репозиторной. Из цены
  ранг не выводится (GPT-5.5 стоит как Sol и слабее его). Модель без ранга —
  «сила неизвестна», её вердикт действительным НЕ считается: утверждать
  «этого достаточно» про модель, о которой ничего не известно, нельзя.
  **На back-check ранг не распространяется намеренно**: там сильная модель хуже
  слабой (чинит кривой английский на лету и прячет искомую ошибку), шкалы нет,
  и потому свежая проверка любой моделью считается сделанной. Нужен другой
  взгляд — отдельный прогон, он идёт со `skip_cached=False`. Единственное
  исключение: `bc["model"] == seg["provider"]` — обратный перевод делала та
  самая модель, что писала текст. Она вернёт свой замысел, а не то, что
  в тексте написано; раньше это лечилось сменой модели в списке, теперь смена
  модели ничего не перезапускает, поэтому случай назван явно. **Прогон при
  таком совпадении сам берёт запасную модель** (`_backcheck_model`,
  `BACKCHECK_FALLBACK_MODEL`): повторный вызов той же моделью давал бы вечную
  переплату — результат выполнялся, не зачитывался и оплачивался заново каждым
  прогоном. На фронтенде этому соответствует группа `self` в `BC_DEFAULT_GROUPS`.
- **Состав прогона считает сервер (`POST /api/projects/{pid}/run-plan`).**
  Смету и состав раньше считал браузер своими предикатами, а работу отбирал
  сервер своими — разойтись они были обязаны: список сегментов у составного
  прогона ОДИН, объединение целей всех шагов, и каждый шаг брал оттуда всё, что
  проходило ЕГО серверную проверку, а не то, что человек отметил галочками
  в карточке соседнего шага. Снятая галочка уменьшала смету, но не работу.
  `_plan_step` использует те же `_backcheck_cached` / `_termcheck_cached` /
  `_check_stale` / `_repairable`, что и прогон, и возвращает НЕ ТОЛЬКО числа,
  но и причины (`runs`/`skips`): «пропущено 970» без причины — не отчёт,
  а отговорка, после которой человек идёт подбирать галочки наугад. Новый шаг
  обязан появиться и в `_plan_step` — иначе карточка снова начнёт врать.
- Back-check кладёт в `seg["backcheck"]` балл, модель и `target_hash`. По хешу повторный
  прогон понимает, что пересчитывать нечего; `/api/projects/{pid}` добавляет производный
  `stale`. Судья вызывается только внутри СВОЕЙ зоны (`_judge_zone`; у короткого
  оригинала она открыта до нуля) — вне её отсутствие `judged` не значит
  «недопроверено». Верна ли отметка `judge_skipped: "hard"`, решает
  `_hard_mark_trusted`: записи НЫНЕШНИХ правил (`backcheck.v ==
  BACKCHECK_VERSION`) верим сразу, а у записи постарше отметка могла стоять
  за потерянный термин, который жёсткой находкой больше не считается, —
  там ей верят, только если `terms_lost` пуст либо в причинах есть
  объективная находка. Слепо не верить всем старым записям нельзя: тысячи
  сегментов с настоящим расхождением чисел поехали бы к судье платно.
  **Спрашивать это надо одним предикатом** (`_judge_pending`) — им пользуются
  и `_backcheck_cached`, и `needs_judge`; две формулы дали бы противоречащие
  числа под соседними кнопками.
- **Правила подсчёта версионированы (`medical_qa.BACKCHECK_VERSION`), и версия
  лежит в записи (`backcheck.v`).** `target_hash` сторожит ТЕКСТ, а не правила:
  когда 25.08 потерю термина ограничили приказными записями, а обрезку основ
  заменили сравнением форм слова, 798 сегментов боевого проекта остались
  с оценками по старым правилам — текст не менялся, `_backcheck_cached` считал
  их свежими, и пересчитать их не мог никто. У 303 из них судья был погашен
  как при жёсткой находке, то есть претензию, выведенную морфологией, стало
  нечем обжаловать. Меняешь формулу, состав жёстких находок или полосы —
  поднимай версию.
  **Пересчёт БЕСПЛАТНЫЙ** (`_rescore_backchecks`, `POST /api/projects/{pid}/backcheck/rescore`,
  `dry_run` по умолчанию): обратный перевод, оригинал и косинус лежат в самой
  записи, глоссарий берётся нынешний, а `run_backcheck` — чистая функция от них.
  Косинус передаётся ГОТОВЫМ числом, а не `semantic_fn`: ленивый вариант полез
  бы считать эмбеддинги, то есть пересчёт стал бы платным. Вердикт судьи —
  оплаченная работа, он применяется заново поверх свежего балла, а не
  выбрасывается. `force=true` пересчитывает и записи своей версии: это нужно
  после правки ГЛОССАРИЯ (понижение записи убирает её из приказных, а претензия
  «потерян термин» по ней остаётся в сохранённой оценке и держит балл).
  **Проходом при старте пересчёт НЕ идёт** намеренно: он зовёт `_verified_hits`
  на каждый сегмент, а это ~13 мс — полминуты заблокированного единственного
  воркера на проекте в 2700 строк, то есть отвалившийся по таймауту деплой.
  Правило то же, что у выноса глоссария и пачек автоодобрения: посчитали,
  показали числа, человек нажал. Прежние записи уходят файлом
  в `data/backups/backcheck-{stamp}.json` и возвращаются
  `POST /api/backcheck/rescore/{stamp}/undo`.
  Отчёт называет и расширение донорской базы (`machine_clean`): поднявшийся балл
  делает сегменты годными в источники для глоссария, и молчать об этом нельзя.
- **Полосы шкалы (`BACKCHECK_BANDS`) посажены на пороги, по которым система
  принимает решения.** Верх зоны судьи (97), `JUDGE_FLOOR_NONE` (95), порог
  донора глоссария (`backcheck_min`, 90) — границы полос; `JUDGE_CAP["major"]`
  (70) — верх КРАСНОЙ полосы, `JUDGE_CAP["critical"]` (45) и потолок «обратный
  перевод про другое» (40) — внутри красных. Иначе вердикт судьи «смысл
  расходится» красился бы предупреждением. Прежние границы называли «Смысл
  поплыл» уже 71-79, то есть половину уцелевших слов, — а живой обратный
  перевод ВСЕГДА перефразирует, и recall 0.6-0.8 у ВЕРНОГО перевода это норма:
  под тревожные подписи попадало 22% боевого проекта. Ключи полос переименованы
  под настоящие границы. **Копия списка на фронтенде ровно одна** —
  `BC_BANDS_FALLBACK` в `ui.jsx`, оттуда же `bcScoreColor`, которым красят балл
  и таблица редактора, и карточка сегмента, и экран экспорта. Лесенок вида
  `score >= 95 ? зелёный : >= 80 ? жёлтый` в `.jsx` быть не должно: после сдвига
  границ они дают трём экранам три разных цвета у одного балла.
- **Штраф за потерянный термин — ДОЛЯ сегмента** (`_term_lost_penalty`,
  `BACKCHECK_PENALTY["term_lost_full"]`), а не плоские −25 за термин. Слова
  термина нет в обратном переводе — значит `_content_recall` УЖЕ вычел их
  из балла, и плоский штраф сверху был вторым счётом за ту же потерю,
  одинаковым и для одного слова в сорокасловном абзаце, и для трёхсловной
  фразы в сегменте из восьми слов. В предельном случае (весь сегмент —
  потерянные термины) штраф равен прежнему потолку 50; на коротком оригинале
  он поэтому СТРОЖЕ прежнего, и называть правку послаблением неверно.
  Обратная сторона: балл перестал быть сторожем этой потери на длинном
  сегменте, поэтому у ремонта заведён отдельный счётчик
  (`_repair_scores["terms_lost"]`). Сверяется он там, где ремонт перепроверял
  back-check, — иначе сравнивать не с чем: у протухшей записи счётчик `None`,
  а `None` означает «неизвестно», а не «чисто». В этом отличие от `gloss`
  и от регистра: те бесплатны и потому считаются всегда, а этот держится
  на платном обратном переводе. Без него ремонт мог принять правку,
  потерявшую термин, а следующий прогон завёл бы по ней новую находку:
  второй платный заход. Считается он тем же `_terms_lost_open`, что и
  претензия ремонта, — иначе ремонт откатывал бы правку из-за потери,
  которую сам же претензией не считает.
- **Потерю термина back-check считает ТОЛЬКО по приказным записям**
  (`_verified_hits`, тот же расчёт, что у `_gloss_misses` и `/glossary-impact`).
  Раньше туда уходил полный `_get_context` — и подсказки автоимпорта тоже, —
  а балл снижался за то, что обратный перевод не сохранил ПОДСКАЗКУ. Модели
  её игнорировать разрешено прямо в промпте («use these exact translations»
  только для `verified`), и наказывать за принятое разрешение нельзя. На боевом
  проекте это давало 56 спорных сегментов из 67: балл держали «лёгких»,
  «высокой», «оценка», «метод» — падежные формы обычных слов, которым сверка
  смысла УЖЕ проставила `rule: false`. Хуже: потерянный термин считался жёсткой
  находкой, поэтому к таким сегментам ещё и судья не приходил.
- **«Пережил ли термин круг» сравнивает ФОРМЫ СЛОВА, а не обрезки основ**
  (`_same_word_form`, `_words_of`). Обрезка до шести букв режет русское слово
  ровно по окончанию: «высокой» → `высоко`, «высокую» → `высоку`. Слово в
  обратном переводе есть, а проверка объявляет термин потерянным и роняет балл
  на ровном месте. Совпадением считается общий префикс не короче четырёх букв
  И не меньше 60% короткого из двух слов. Порог подобран так, чтобы
  «противотуберкулёзный» против «туберкулёзного» НЕ сошлись: отвалившаяся
  приставка — настоящая потеря, ради которой проверка и заведена. `_stems`
  при этом не тронут намеренно: он считает `_content_recall`, то есть ВСЕ
  баллы проекта, и его правка была бы пересчётом всего разом.
- **Зона судьи зависит от сегмента (`_judge_zone`), а не только от балла.**
  Низ шкалы закрыт потому, что там решение уже принято детерминированной
  проверкой. На коротком оригинале никакого решения принято не было: доля
  выживших основ при одном-двух содержательных словах бывает только 0 или 1,
  промежуточных значений нет физически, и любой синоним в обратном переводе
  роняет балл в ноль при ВЕРНОМ переводе — «Фтизиатрия → Phthisiology →
  Фтизиология», «плевры → pleura → плевра», «моноустойчивый → monoresistant →
  монорезистентный». На боевом проекте так вышло у 40 сегментов, и все они
  лежали ниже `JUDGE_ZONE`, то есть приговор выносила обрезка слова до шести
  букв, а обжаловать его было некому. Порог «меньше трёх РАЗНЫХ содержательных
  основ» живёт в `medical_qa.lexically_blind` — там же, где `_content_recall`,
  иначе «содержательное слово» однажды станет двумя разными понятиями.
  Балл при этом НЕ поднимается: выдумать число вместо измерения хуже, чем
  признаться, что его нет. `run_backcheck` пишет причину прямым текстом,
  поднять балл вправе только судья (`JUDGE_FLOOR_NONE`).
  Отсюда три следствия, которые нельзя ослаблять:
  1) **`judge_skipped: "zone"` больше не считается законченной проверкой.**
     Отметка вынесена ПРЕЖНЕЙ зоной, а зона теперь у каждого сегмента своя:
     верить отметке значит навсегда закрыть от судьи ровно те сегменты, ради
     которых зону и открыли. `_backcheck_cached` считает зону заново, а из
     отметок безусловной осталась только `"hard"` — объективную находку
     (числа, единицы, отрицание) судья отменить не вправе при любой длине;
  2) **признак «судья ещё не смотрел» считает СЕРВЕР** (`backcheck.needs_judge`
     в `_segment_for_client`), а браузер его читает. Зона выводится из русской
     морфологии `medical_qa`; повтори её в `.jsx` — и состав под кнопкой
     «запустить только этот шаг» разойдётся с серверным на коротких сегментах,
     то есть под соседними кнопками встанут противоречащие числа;
  3) верх зоны не двигается: выше 97 спорить не о чем при любой длине.
  **Обратный перевод при этом НЕ покупается второй раз.** Единственная
  недостача — судья, а готовый обратный перевод лежит в сегменте: условие
  переиспользования узкое (`_backcheck_cached` БЕЗ судьи говорит «закончено»,
  С судьёй — «нет»), поэтому прогон другой моделью (`skip_cached=false`) сюда
  не попадает и делает перевод заново. Модель в записи называется та, что
  перевод и делала, — подписать чужой работой выбранную в списке значит
  соврать о происхождении оценки. На боевом проекте так экономятся все 52
  вызова: платим только за судью.
  **«Потерян термин» жёсткой находкой не считается НИ ПРИ КАКОЙ ДЛИНЕ**
  (`_hard_issue(issues)`). Проверка «пережил ли термин круг» — то же сравнение
  основ и префиксов, что и `_content_recall`/`_same_word_form`, только суженное
  до слов глоссария. Это не независимая улика, а тот же счёт, сказанный второй
  раз, и ошибается он ровно там, где ошибается морфология: «туберкулёз лёгких»
  обратный перевод возвращает как «лёгочный туберкулёз», «вдохе» — как «вдоха».
  Считая её жёсткой, мы гасили судью — то есть отнимали апелляцию у претензии,
  которую апелляция и должна снимать: на боевом проекте так вышло у 303
  сегментов. Числа, единицы, отрицание и подмена стороны (`BACKCHECK_HARD_TYPES`)
  от длины и от морфологии не зависят и остаются жёсткими ВСЕГДА.
  **Судья, сказавший «severity: none», СНИМАЕТ претензию про термин при любой
  длине.** Соблюдению глоссария это ничем не грозит: «стоит ли утверждённый
  вариант в ПЕРЕВОДЕ» считает отдельная детерминированная проверка
  (`_gloss_misses` / `/glossary-impact`), и вердикта судьи она не спрашивает.
  **Снятая претензия не возвращается через строку причины.** `_repair_findings`
  разбирает `backcheck.reasons` подстрокой русской фразы, а отречение судьи
  само содержит «потерян термин: X» — поэтому по причинам ремонт берёт только
  ОБЪЕКТИВНЫЕ находки (`BACKCHECK_OBJECTIVE_REASONS`), а претензия про термин
  выставляется отдельной строкой `kind: "term_lost"` из `terms_lost`, с учётом
  вердикта арбитра. Иначе один и тот же сегмент шёл в ремонт с претензией,
  которую только что отменили, — платный вызов с заранее известным исходом.
  **«Судья ещё не смотрел» считает ОДИН предикат `_judge_pending`** — и состав
  прогона (`_backcheck_cached`), и признак `backcheck.needs_judge`, уезжающий
  браузеру. Две формулы разошлись бы на записях со старой отметкой `"hard"`:
  прогон брал бы 303 сегмента, а «Запустить только этот шаг» их не видел
  и смета судьи их не считала.
  **На коротком оригинале судью слушают и на `minor`** — но только вместе
  с `same_meaning: true`. Балл там не измерение, а вердикт судьи —
  единственная мера; «плевры → pleura → плевра» он описывает как «различается
  только грамматическая форма» и ставит `minor`, что по вопросу back-check
  («пережил ли смысл круг») есть чистое «да». Без подъёма балл оставался
  нулём — приговором, которого никто не выносил. На длинном сегменте `minor`
  не поднимает ничего: там ноль что-то значил.
  **Подняв балл, судья СНИМАЕТ претензию про потерянный термин** — и говорит
  об этом в `reasons`. Оставить её значит отправить верный перевод в ремонт
  по замечанию, которое только что отменил тот, кто читал оба текста.
  **Молчание судьи — «не знаю»** (`judge_skipped: "failed"`): отметка в сегмент
  ставится, но законченной проверкой не считается. Спросить ещё раз правильно,
  и теперь это дёшево — обратный перевод берётся готовым.
  **Тумблер «Судья» выключен по умолчанию и не переживает перезагрузку**
  (это разрешение на прогон, а не настройка). Значит открытая вниз зона сама
  по себе не чинит ничего: без судьи `_backcheck_cached` закрывает сегмент
  сразу, балл 0 остаётся нулём, а честная причина в `reasons` даже не
  записывается — back-check не перезапускается. Поэтому корзина `/analysis`
  ОБЯЗАНА называть такие сегменты своей причиной (`CLEAN_LEX_BLIND`).


## Практики работы с ИИ-агентом (общие, во все проекты)

7. **База знаний.** Держи доки проекта в базе знаний; на больших проектах разбивай на файлы, а в CLAUDE.md оставляй карту «какой файл под какую задачу». Обновляй по ходу.

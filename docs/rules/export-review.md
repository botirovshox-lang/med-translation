# Сверка первой выгрузки нового файла: «до/после» → правила

Правило владельца сервиса (13.10.2026): **каждая первая выгрузка нового файла
сверяется с оригиналом**, а каждый найденный дефект становится ПРАВИЛОМ — кодом,
тестом и записью в `docs/rules/pdf-reading.md` — вне зависимости от проекта
и языка. Разовая правка одного файла правилом не считается: тот же дефект
повторится на следующем файле клиента.

Кто делает: агент-разработчик (Claude Code) в сессии с владельцем. Сервер
только ставит файл в очередь и пишет владельцу в Telegram.

## 1. Очередь

- Сервер: `_export_review_note` в `main.py` при КАЖДОЙ выгрузке; строка
  очереди (`STATE["exportReviews"]`) заводится, только если этот файл
  (номер проекта + `sourceSha`) ещё не выгружался. Замена файла другим —
  новая строка. Двери: `GET/POST /api/admin/export-reviews[/{rid}]`, только
  суперпользователю. Страж — `tests/test_export_review.py`.
- Агент: **в начале каждой сессии** `python tools/export_review.py list` и
  разбор всего, что лежит в очереди (по одному файлу за раз).

## 1а. Случаи проверки перед выдачей (ТЗ `docs/plans/photo-first-export.md`, этап 4)

- Сервер: проверка перед выдачей (`_job_prepress_body`) на каждое место,
  оставшееся после кругов правок с видимым браком (`USER_CODES`, уверенность
  от `MIN_CONF`), пишет случай `data/sources/prepress_cases/<орг>/<проект>/<n>`
  (.json — код, признаки места, версия кода; .jpg — «оригинал | итог»).
  Потолки: 5 на файл, 20 неразобранных на организацию, гостей не пишем; срок —
  30 суток (политика, п. 6.2.3), удаление проекта уносит его случаи. Двери:
  `GET /api/admin/prepress-cases`, `…/{орг}/{проект}/{n}/image`,
  `POST …/{орг}/{проект}/{n}` — только суперпользователю.
- Агент: **в начале каждой сессии** `python tools/prepress_cases.py list`;
  `pull DIR` (вне репозитория) — посмотреть вырезки, свести случаи в ВИДЫ;
  на вид — правило (код + тест + `pdf-reading.md`), затем фото-бенч
  (`tools/photo_bench.py --check`), `corpus_offline` и эталоны 8/19/20/14 не хуже
  → выкат (решение владельца 24.10.2026: не ждать повторения у второй
  организации); случаи — `done … --rule Ю…` или `wont` (не наш брак). DIR
  удалить после разбора.

## 2. Разбор одного файла

1. **Скачать.** `python tools/export_review.py fetch PID DIR` — документ
   проекта, карта исходника, оригинал, свежая выгрузка. DIR — вне репозитория
   (это данные клиента).
2. **Сверить время.** Выгрузка могла быть сделана ДО того, как проект
   пересобрался по новым правилам (авто-пересборка строк и надписей идёт при
   открытии проекта, раздел И). Сравнить время выгрузки (`exportHistory.when`)
   с временем последней пересборки (`data/backups/reimport-PID-*`) и
   `parseRules`/`layerRule` проекта. Если выгрузка старее — собрать свежую
   (без записи в «Скачать»: подменить `_export_path` во временный файл,
   скрипт через `tools/prod_run.sh`) и сверять её. Ошибка этого шага уже
   стоила разбора: выгрузка (7) проекта 14 была сделана за 15 с до пересборки.
2б. **Начать с приёмки** (Ч5, `backend/export_qa.py`): сервер сам сверил
   готовый файл с оригиналом и положил отчёт рядом с ним (`<файл>.qa.json`:
   коды, страницы, рамки, номера строк), а у первой выгрузки нового файла
   платный взгляд модели уже подтвердил/снял находки правил и назвал то,
   чего правила не видят (раздел `vision`). Это СПИСОК МЕСТ для критиков,
   а не замена им: подтверждённое моделью ищется глазами первым. Повторный
   взгляд — `POST /api/admin/export-qa/{pid}` (суперпользователю).
   Сверить ОФЛАЙН текущим кодом — `python tools/export_qa.py DIR`.
3. **Нарисовать пары.** `python tools/export_review.py pages DIR` —
   `DIR/pairs/NN.png`: слева оригинал, справа выгрузка (у PDF-«ленты» —
   виртуальными страницами).
4. **Критики — двое, отдельными субагентами, по парам страниц:**
   - *критик-дизайнер* (вёрстка): кегль и начертание против оригинала и
     соседей, текст за рамкой/плашкой/кольцом, наложения, заплатки шире
     своего места, пункты не у своих значков, переносы, направление дуги,
     выключка, пропавшие маркеры, остатки оригинала;
   - *критик-переводчик/редактор* (текст): смысл, кальки, разнобой одного
     термина и одной надписи в разных местах, перевод по кускам (одна
     надпись — несколько сегментов), знаки (< > ≤ ≥ ±, степени, индексы,
     сноски), регистр, сокращения, литература и адреса.
   Каждый отдаёт список: страница, место, что видно, как в оригинале.
5. **Свести в ВИДЫ.** Дефекты одной природы — один вид (образец разбора:
   виды A–G проекта 14, раздел С в `pdf-reading.md`). У каждого вида:
   причина с доказательством (функция, числа), ОБЩЕЕ правило, где в коде,
   риск для других документов, тест.
6. **Внедрить правило.** Код + тест (синтетический PDF через
   `tests/pdf_fixture.py` или юнит) + запись в `docs/rules/pdf-reading.md`
   (симптом → причина → правило → код → страж). Меняются абзацы разбора —
   поднять `pdftext.RULES_VERSION`.
7. **Регрессия на эталонах.** Выгрузить кодом ДО и ПОСЛЕ проекты-эталоны
   (сейчас: 8 — книга RU→UZ-CYRL, 19 — статья EN→RU, 20 — статья EN→UZ,
   14 — инфографика EN→RU) и сравнить постранично: что изменилось, в лучшую
   ли сторону, нет ли новых наложений и вылезаний (`stats`: collisions,
   overflow, fOffShare). Плюс полный прогон тестов.
8. **Критик по дифу** (reviewer): регрессии, дыры в тестах, частные случаи,
   выданные за общее правило.
9. **Отчёт «до/после»** страницей-артефактом: вырезки оригинал | было | стало
   по каждому виду, что починено, что нет и почему. **Коммит и выкат — только
   после «ок» владельца.**
10. **Закрыть строку очереди:** `python tools/export_review.py done RID
    --report URL --note "виды…"` (или `skip` с причиной).

## 3. Деньги

Платные шаги разбора (перевести строки, появившиеся после пересборки; прочитать
надписи на картинках) — без вопроса до **$1 на файл**; дороже — спросить
владельца, назвав сумму. Платные прогоны «ради проверки» (перевести заново
готовое) — нет.

## 4. Чего не делать

- Не чинить один файл правкой данных проекта вместо правила.
- Не выдавать частный случай за общее правило: правило формулируется через
  устройство файла (рамка, колонка, значок, дуга, плашка), а не через слова
  этого документа.
- Не класть файлы клиента в репозиторий (`backend/data/` в .gitignore).
- Не писать на боевой сервер мимо `tools/prod_run.sh`.

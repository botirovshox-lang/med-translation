# CLAUDE.md — Medical CAT Translator (корень репозитория)

Правила для AI-ассистентов и разработчиков. Прочти перед любыми изменениями.

## Что здесь актуально

- **`backend/main.py`** — весь продакшен-бэкенд (FastAPI, ~25 эндпоинтов). Одним файлом, это осознанно.
- **`backend/medical_qa.py`** — медицинский QA (структурные/числовые проверки, обратный перевод).
- **`frontend/`** — React 18 **без сборки**: UMD + Babel standalone, `.jsx` компилируются в браузере.
- **`deploy/medcat.service`** — источник истины для systemd-юнита (копируется в `/etc/systemd/system/`).
- **`med_translation/`** — legacy Streamlit-код; из него используются только модули
  (глоссарий TSV в `assets/glossary/`, `medical_qa`, `tm`, `db`, `pipeline`) через `sys.path` в `main.py`.
- **`med_translation/CLAUDE.md`** — правила отдельного legacy-подпроекта (TM-билдер из PDF), не про этот бэкенд.

## Жёсткие инварианты (нарушение = потеря данных)

1. **Ровно 1 uvicorn worker.** `STATE` — глобальный dict в памяти процесса,
   `state.json` — его снапшот. Два воркера затирают данные друг друга.
2. **Все мутации `STATE` заканчиваются `save_state(STATE)`.** Запись атомарна
   (tmp + `os.replace` под `_SAVE_LOCK`) — не заменяй на прямую запись.
3. **Писать на диск можно только в `backend/data/`** (systemd `ProtectSystem=full`,
   `ReadWritePaths`). Экспорты — в `data/exports/`, бэкапы — в `data/backups/`.
4. **Никаких демо-заглушек в target.** Ошибка перевода → HTTP 502 / `{"ok": false, "error": ...}`,
   сегмент не трогать. То же на фронтенде: не подставлять фейковый текст при недоступном сервере.
5. **Изменил `frontend/js/*` → бампни `?v=` во всех строках `frontend/index.html`.**
   Иначе пользователи получат старый кэш и «загадочные» баги.
6. **Модели и цены живут только в `OPENAI_MODELS`.** Фронтенд берёт их через
   `/api/models`; хардкод id или цены в `.jsx` — ошибка.
7. **Платные прогоны (перевод, back-check, судья) не запускай ради проверки.**
   Логику отбора проверяй запросами, которые заведомо попадают в кэш.
8. **Автоматически глоссарий пополняется только уровнем `auto`.** Находки идут
   в `STATE["termQueue"]` и ждут решения. Автоодобрение (`/api/term-queue/auto-approve`)
   раскладывает однозначных кандидатов само, но пишет их подсказкой (`tier: auto`),
   которую модель вправе игнорировать. Приказом (`tier: verified`) запись становится
   от человека (кнопка одобрения в очереди), от трёх независимых чистых сегментов
   либо от **внешнего справочника** (`backend/authority_data/`, см. `authorities.py`).
   В медицине, фарме и юриспруденции (`AUTO_APPROVE_BY_DOMAIN`) согласия сегментов
   для приказа НЕ хватает — там приказ даёт только человек или справочник.
   **Справочник обходит запрет области намеренно и законно**: запрет касается
   САМОодобрения (система заверяет собственный перевод), а справочник — источник
   вне контура. Тумблер «только подсказки» (`max_tier`, ключ `cap_soft`) сильнее
   справочника: это просьба человека на конкретный запуск.
   Подтверждение сегмента-донора приказа НЕ даёт: человек заверил перевод строки,
   а не правило для всех будущих текстов. Правило «приказ
   даёт человек» и есть защита от закрепления собственных ошибок перевода;
   ослаблять её ради удобства нельзя.
9. **Правки TM и глоссария не переписывают чужой текст молча.** Подтверждение возвращает
   список повторов, распространение — отдельная команда `/propagate`, подтверждённые
   сегменты по умолчанию не трогаются (так же ведут себя Phrase и Trados).
10. **Все `/api/*` требуют токен сессии** (`Authorization: Bearer`), проверка — в мидлвари
   `require_token`. Публичны только `PUBLIC_API_PATHS` (login, logout, health);
   расширять этот список — значит открыть эндпоинт всему интернету.

## Деплой (VPS 31.129.100.106, домен trasnlateuz.duckdns.org)

```bash
cd /opt/med-translation && git pull && git log -1 --oneline   # НЕ прячь пул за | tail: код возврата пропадёт
systemctl restart medcat
# поднимается ~15 с (state.json + глоссарий) — сразу после рестарта curl получит refused
for i in $(seq 1 15); do sleep 2; curl -s --max-time 5 http://127.0.0.1:8000/api/health && break; done
```
Секреты в `/etc/medcat/env` (не в git): `APP_PASSWORD`, `OPENAI_API_KEY`.
`GOOGLE_TRANSLATE_API_KEY` больше не используется — Google убран из системы.
**`APP_PASSWORD` обязателен** — дефолта в коде больше нет. Если переменная пуста, сервис
стартует со случайным паролем и пишет его в journal (`journalctl -u medcat | grep APP_PASSWORD`),
то есть все пользователи окажутся заперты снаружи. Необязательные: `ALLOWED_ORIGINS`
(CORS-белый список, через запятую), `SESSION_TTL_HOURS` (по умолчанию 12).

Репозиторий принадлежит `medcat`, деплой идёт от root: `/opt/med-translation` прописан
в `safe.directory` root'а, часть объектов `.git` root-овая — пул от `medcat` уже не пройдёт.

## Известные особенности

- **Google Translate убран.** Переводит ТОЛЬКО выбранная модель: бесплатный движок
  не знал предметной области, игнорировал глоссарий и давал текст, который всё равно
  чинили платными прогонами. Нет ключа OpenAI — нет перевода: 503 с внятной причиной,
  не заглушка и не «черновик бесплатным движком». Ключ требуется, только если хоть
  один сегмент придётся переводить: порция из одних совпадений с памятью работает
  без него. `provider: "google"` и `route: "GOOGLE_SAFE"` остаются в исторических
  сегментах — это факт о том, чем их перевели; новые так не помечаются.
- **Отбора по `risk` при переводе больше нет.** Он делил сегменты между Google
  и моделью, и запуск «не той» кнопки молча оставлял половину проекта
  непереведённой. `risk` — по-прежнему длина сегмента, но на движок не влияет.
- **Промпт перевода собирает `_translate_system`** — отдельно от вызова модели,
  чтобы его можно было проверить тестом: от того, уходит ли запись глоссария
  приказом или подсказкой, зависит, повторит ли модель чужую ошибку.
- **Пять вкладок вместо девяти.** `TabKnowledge` = глоссарий + память переводов
  (две справочные базы одной области), `TabAnalysis` = смета + итог + замечания +
  доска + статистика (все отвечали на вопрос «что не так и во что обойдётся»).
  Старые ключи вкладок живы в `tabMap`: на них ведут ссылки изнутри страниц.
- `load_state()` при битом `state.json` сохраняет его как `state.corrupt-*` и
  поднимает свежайший бэкап из `data/backups/` (48 почасовых копий).
- PDF-экспорт не реализован; DOCX/XLSX собираются по-настоящему (python-docx / openpyxl).
- `seg["risk"]` — длина сегмента (`words > 30 → high`, `> 8 → medium`), а НЕ медицинская
  опасность. Не подписывай его как «риск по содержанию»: в медицинском инструменте это
  опасное враньё. Настоящий `risk_score` даёт только медицинский QA.
  **Писать в `risk` результат проверки нельзя.** Medical QA ставила туда свою
  оценку и тем перетирала длину, по которой раньше выбирался движок. Движок теперь
  один, но поле по-прежнему описывает ОРИГИНАЛ, а не качество перевода.
  Медицинская опасность живёт в `risk_score`/`risk_color`; миграция при загрузке
  возвращает `risk` длину.
- **Проверка не меняет статус подтверждённого сегмента.** Medical QA не трогает
  ни буквы текста, поэтому и разжаловать решение человека не вправе — находка
  видна по `risk_color`/`qa_issues`, а вкладка QA показывает подтверждённые
  сегменты с критическими замечаниями отдельно. Статус меняют только те, кто
  переписал текст (перевод, ремонт, переперевод), и всегда на `review`.
- **Область записи: языковая пара + тематика.** Глоссарий и TM одни на сервис,
  проекты разные. `_get_context` отдаёт только записи из области проекта
  (`_project_scope`), TM — только свою языковую пару. Записи без полей `lang`/`domain`
  читаются как `RU→EN` + `medical` (весь исторический импорт именно такой), поэтому
  массовой миграции нет — не добавляй её, это лишние сотни килобайт в каждом
  сохранении `state.json`. Новые записи область получают всегда.
- **Автоодобрение кандидатов (`_auto_verdict`).** Однозначным считается только то,
  что подтверждают сигналы, не зависящие от языка и тематики: единственность варианта
  в очереди, согласие НЕЗАВИСИМЫХ сегментов-доноров (`cand["segments"]`, ключ
  `"проект:сегмент"` — номера сегментов уникальны лишь внутри проекта) и чистые оценки
  чужих прогонов (`_machine_clean`: back-check ≥ порога, termcheck без находок, текст
  не переписан авторемонтом, termcheck не пропущен как «нечего проверять»).
  **Независимость считается по РАЗНЫМ исходникам.** Сегменты с `route: "DUPLICATE"`
  и с `propagatedFrom` донорами не считаются вовсе (перевод скопирован, а не получен
  заново), а на приказ нужны доноры с разным текстом оригинала: один и тот же
  заголовок, переведённый трижды, — это одно решение, а не три подтверждения. Кандидат `conflict` не одобряется никогда (у него нет
  готового перевода), `audit` — не меньше чем с двух доноров: это мнение модели
  о собственном переводе. `dry_run=True` — режим по умолчанию, он ничего не меняет.
  Любая пачка откатывается целиком (`/api/term-queue/auto-approve/{batch}/undo`)
  по `autoBatch` и сохранённым `prevTgt`/`prevTier`; автоматика без отката недопустима.
- **Решение по кандидату — про термин, а не про карточку.** Дедупликация очереди
  идёт по паре, с которой кандидат РОДИЛСЯ (`_cand_pair`, поля `origSrc`/`origTgt`):
  одобрение вписывает в `src`/`tgt` решение человека (у `conflict` перевод рождается
  пустым и заполняется только им), и без этой памяти следующий `_harvest_terms`
  не узнавал бы решённого кандидата — одобренный термин возвращался в очередь
  новым. Одобрение закрывает и остальные ОЖИДАЮЩИЕ карточки про тот же термин
  в той же области (`_close_same_term`); отклонение — нет: «эта пара неверна»
  не равно «с термином разобрались». Подрезка очереди снимает решения человека
  последними (`_human_decision`) — на них держится «этот вопрос уже задавали».
- **Сбор терминологии идёт с проверенных сегментов, а не сразу после перевода.**
  `_harvest_terms(via="confirmed")` — на подтверждении человеком (там же рождаются
  кандидаты `conflict`), `_harvest_if_clean` — в конце back-check и termcheck, когда
  обе оценки чистые (`via="auto"`, только готовые пары). Висит на обоих прогонах
  намеренно: порядок выбирает пользователь, и собрать может лишь тот, кто отработал
  вторым.
- **Уровни доверия глоссария.** `tier: "verified"` уходит модели приказом
  («use these exact translations»), `tier: "auto"` — подсказкой, которую разрешено
  игнорировать. 9132 из 10022 записей — массовый автоимпорт (`baldwin_*`), и там есть
  «задний → rear»; ровно так и рождалось «rear cyclitis». Плейсхолдеры Google
  подставляются ТОЛЬКО для `verified`: это принуждение мимо всех проверок.
  Ручная правка и одобрение кандидата поднимают запись до `verified`.
- **Соответствие глоссарию (`/api/projects/{pid}/glossary-impact`).** Одобрение термина
  НЕ переписывает готовые переводы — это осознанно. Расхождения собираются отдельно
  (термин в оригинале есть, утверждённого варианта в переводе нет) и переводятся заново
  пакетом по кнопке. Считается только по `tier: verified`: требовать соответствия
  автоимпорту нельзя, модель вправе его игнорировать. Подтверждённые сегменты
  переводятся заново только по явной галочке (`include_confirmed` у `/batch`,
  работает лишь вместе с `force` и списком id). При этом прежний текст уходит
  в `prevTarget`, статус становится `review`, а отметка `confirmedBy` снимается:
  машина не заверяет сама себя. Без галочки такие сегменты называются поимённо
  в `skipped_confirmed` — прогон не имеет права рапортовать «готово», не сделав
  ничего.
- **Индекс глоссария.** `_get_context` без индекса гонял 10 000 регулярок на сегмент
  (10-17 с CPU). Есть `_gloss_index()` по ключам-началам слов — любая мутация глоссария
  обязана звать `_invalidate_gloss_index()`, иначе поиск будет работать по старым данным.
  Шаблоны терминов компилируются один раз и лежат в `_PATTERN_CACHE`: без этого внутренний
  кэш `re` переполнялся десятью тысячами записей и пересобирал регулярки на каждый вызов
  (134 мс на сегмент против 1 мс).
- **Точное совпадение термина — только по границам слова.** Без этого трёхбуквенные
  записи лезли внутрь чужих слов: «жалобы» → «лоб», «профилактика» → «лак».
- **Предметная область — параметр проекта** (`project["domain"]`, каталог `DOMAINS`).
  Из неё строятся ВСЕ промпты (перевод, проверка терминологии, судья, извлечение
  терминов) и детерминированные правила (`DOMAIN_RULES` в `medical_qa.py`, ключ —
  «область + пара языков»). Хардкодить медицину или RU→EN в новом коде нельзя.
  Нет правил для этой области и пары — проверка МОЛЧИТ, а не срабатывает наугад:
  выдуманная находка хуже отсутствующей. Числа, единицы и соответствие глоссарию
  языконезависимы и работают всегда.
- **Что ещё зашито и мешает продаже — в [BACKLOG.md](BACKLOG.md)** (мультиарендность,
  общий глоссарий, морфология только для русского, бесплатный Google-фолбэк, учёт
  расхода). Правишь что-то из списка — вычёркивай оттуда.
- **Внешние источники (`backend/authorities.py`).** Два вида и разные права:
  **справочник** (`authority_data/*.tsv`) фиксирует пару «оригинал → перевод» —
  совпадение с ним даёт приказ; **корпус** (PubMed для медицины, Википедия для
  любого языка) отвечает на другой вопрос — «есть ли такой термин в языке» —
  и потому только НАЛАГАЕТ ВЕТО (ноль вхождений = калька) или удерживает
  на подсказке, но приказа не даёт никогда. Закон тот же, что у `DOMAIN_RULES`:
  нет источника для этой области и пары языков — МОЛЧИМ. `attested() → None`
  означает «не знаю» (сеть, лимит, нечитаемый ответ) и не должно ни одобрять,
  ни блокировать. Корпус спрашивается только про кандидатов, прошедших все
  остальные проверки, с потолком `AUTO_CORPUS_MAX` и троттлингом под лимит
  источника; в разборе `dry_run` он по умолчанию МОЛЧИТ (иначе открытие
  проекта — минута ожидания), а ответ помечается `corpusPending`.
- **Второй клик (`kind: "apply_terms"`).** Одобряет пачку терминов, затем чинит
  ими сегменты. Состав считается ПОСЛЕ одобрения и берётся из `glossary_impact`
  (только разошедшиеся с утверждёнными терминами), а не из «всех, где есть
  находки»: человек нажал «применить термины», а не «перебрать проект».
  Остановка проверяется ДО записи глоссария — он меняется одним куском.
- **Составной прогон (`kind: "full"`).** Одна кнопка на весь конвейер: порция
  проходит `FULL_RUN_STEPS` подряд — перевод → back-check → термины → Medical QA →
  ремонт. **Порядок задаёт сервер, а не клиент** (клиент выбирает только состав):
  Medical QA берёт готовый обратный перевод из back-check, терминологию собирает
  та из двух проверок, что отработала второй, ремонту нужны находки всех
  предыдущих. У каждого шага СВОЯ модель (`FULL_STEP_MODEL`); незаполненная
  означает «возьми свою по умолчанию», а НЕ модель переводчика — иначе back-check
  идёт той же моделью, что переводила, и перестаёт быть независимой проверкой,
  на которой стоит автоодобрение. Шаг без ключа или модуля не роняет прогон
  (`blocked` → счётчик `step_skips`), но порция, где не отработал НИ ОДИН шаг,
  падает. Внутри перевод идёт с `force=False`, проверки — со `skip_cached=True`.
- **`engine: "auto"` у `/batch`** — движок выбирается посегментно по `risk`
  (`low_engine`, по умолчанию `gpt`). Без него составная кнопка брала бы половину
  сегментов: отбор для `gpt` отбрасывает короткие, для `google` — длинные.
- **`_replace_target` — единственное место, где машина меняет текст сегмента.**
  Правило одно на всех (перевод, подстановка из TM, рассылка повторов): если
  перевод заверял человек, прежний текст уходит в `prevTarget`, статус
  становится `review`, отметка `confirmedBy` снимается — она относилась к тексту,
  которого больше нет. Пакетные прогоны (перевод, ремонт) подтверждённые
  вообще не берут без явного `include_confirmed`.
- **Точное совпадение с TM подставляется только от `quality: "verified"`**
  (`_tm_trusted`) и ставит `translated`, а НЕ `confirmed`: одно подтверждение
  человека на одной строке не заверяет все будущие строки с тем же исходником.
  Память переводов была единственным местом, где чужая ошибка попадала в перевод
  мимо глоссария и мимо всех проверок.
- **`/api/projects/{pid}/analysis`** — итог по проекту одним экраном. Корзины
  обязаны быть ИСЧЕРПЫВАЮЩИМИ: сегмент, не попавший ни в одну, исчезает с экрана,
  и картина выглядит благополучнее, чем есть. Кэш по отпечатку, куда входят и
  сами оценки (балл back-check, число находок), а не только хеши текста.
- **Прогоны идут на сервере (`_JOBS`, `/api/projects/{pid}/jobs`).** Браузер только
  ставит задачу и опрашивает статус: закрытая вкладка больше не обрывает работу.
  Рабочий поток ОДИН и очередь одна — воркер uvicorn один, `STATE` общий, два
  параллельных прогона дрались бы за `state.json`. Задачи живут в памяти процесса:
  рестарт сервиса их теряет (сделанные сегменты сохранены). Остановка мягкая —
  текущая порция досчитывается. Порция, где не прошло НИЧЕГО, роняет прогон
  в `error`: пакетные эндпоинты глотают ошибки посегментно, и без этого мёртвый
  ключ выглядел бы как «выполнено».
- **Автоматический ремонт (`seg["repair"]`).** Чинит по конкретным находкам, после чего
  перепроверяет ТЕМИ ЖЕ проверками и оставляет новый текст, только если оценка не упала.
  Иначе — откат вместе с восстановлением прежних проверок. Статус после ремонта `review`,
  не `confirmed`: автоправка не заверяет сама себя. Один заход на один текст
  (`repair.source_hash`), производный `tried` — как `stale`.
  **Соответствие глоссарию — такая же находка ремонта** (`_gloss_misses`, `kind: "gloss"`),
  считается тем же расчётом и по тем же `verified`, что и `/glossary-impact`: разойдись
  они в определении нарушения — переписывали бы сегмент друг за другом по кругу.
  Все проверенные записи сегмента уходят в промпт ремонта целиком, даже нетронутые:
  без этого модель, починив одно, свободно выбивала утверждённый термин в другом месте.
  Число нарушенных терминов входит в `_repair_scores` и сверяется ВСЕГДА, а не только
  когда чинили из-за глоссария, — эта оценка не стоит ни одного вызова модели.
- **Внутри порции вызовы идут параллельно** (`_run_parallel`, `RUN_WORKERS`, по умолчанию 6).
  Вызов модели — это ожидание сети, а не процессора. Мутации STATE применяет основной
  поток: рабочие функции возвращают результат, а не пишут в общие структуры. Всё, что
  пишет в общее (`_queue_term`), обязано брать лок. Поднимать RUN_WORKERS выше лимитов
  аккаунта бессмысленно — начнутся 429 и повторы.
- **Во время прогона клиент забирает только обработанные сегменты**
  (`POST /api/projects/{pid}/segments/fetch` + `job.recent`). Полный проект на 2670
  сегментов весит 5 МБ; тянуть его каждые несколько секунд — мегабайты трафика
  и подвисающая таблица.
- **Экономия вызовов — часть контракта прогонов.** Повторы внутри порции (одинаковый
  исходник в переводе, одинаковая пара оригинал+перевод в back-check и termcheck)
  считаются один раз; судья не вызывается при жёсткой находке (его вердикт всё равно
  ничего не изменит); эмбеддинги считаются лениво и кэшируются; Medical QA берёт готовый
  обратный перевод из `backcheck`; termcheck не тратит вызов на сегменты без слов.
  Добавляя новый прогон, добавляй и дедупликацию — иначе пакет на 2000 сегментов
  оплачивает одни и те же заголовки десятки раз.
- **Проверка терминологии (`seg["termcheck"]`) — не back-check.** Back-check спрашивает
  «пережил ли смысл обратный перевод» и на кальке всегда отвечает «да»: «rear cyclitis»
  дословно возвращается как «задний циклит». Termcheck смотрит только на перевод и
  спрашивает «нормальный ли это термин целевого языка». Кэш по `target_hash` + модели,
  производный `stale` — как у back-check.
- Back-check кладёт в `seg["backcheck"]` балл, модель и `target_hash`. По хешу повторный
  прогон понимает, что пересчитывать нечего; `/api/projects/{pid}` добавляет производный
  `stale`. Судья вызывается только внутри `JUDGE_ZONE` — вне её отсутствие `judged`
  не значит «недопроверено».


## Практики работы с ИИ-агентом (общие, во все проекты)

7. **База знаний.** Держи доки проекта в базе знаний; на больших проектах разбивай на файлы, а в CLAUDE.md оставляй карту «какой файл под какую задачу». Обновляй по ходу.
8. **Самопроверка.** Проси агента критиковать свой план (риски/альтернативы), писать чек-лист под задачу и проходить его после; крупную работу — аудитить отдельным чатом.
9. **Тесты.** Тест на каждую значимую функцию, прогон после каждой задачи, тест заложен ещё в ТЗ, авто-прогон при коммите (Git-хук/CI).
10. **Логи.** Логируй важные функции — при сбое читаем лог, а не правим наугад по всем файлам.

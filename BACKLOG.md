# Бэклог: что мешает продавать сервис

Аудит от 18.08.2026. Здесь только то, что **зашито в код** и упирается в продажу
сервиса за пределы одного медицинского проекта на паре RU→EN.

Формат: **что зашито → чем мешает → что делать**. Оценки грубые, в человеко-днях.

Отметки: 🔴 блокирует продажу · 🟡 всплывёт на первом же клиенте · ⚪ терпит

---

## 1. Мультиарендность и доступ

### 🔴 Один пароль на весь сервис — 5-8 дней
`APP_PASSWORD` в `/etc/medcat/env`, одна общая сессия ([main.py:727](backend/main.py#L727)).
Все клиенты видят **чужие проекты, глоссарий и память переводов**. Продать двум
заказчикам одновременно физически нельзя: медицинские документы одного будут
лежать в интерфейсе другого.

Нужно: пользователи с паролями, организации (tenant), проекты и словари внутри
организации, роли (переводчик / редактор / администратор). Это же снимает вопрос
«кто подтвердил сегмент» — сейчас автор правки не фиксируется нигде.

### 🔴 Глоссарий и TM общие на всю установку — 2-4 дня
`STATE["glossary"]`, `STATE["tm"]` — плоские списки без владельца. Терминология
заказчика A попадёт в переводы заказчика B. Для продажи глоссарий должен
принадлежать организации, а часть — конкретному проекту (в CAT-инструментах это
норма: разные термбазы под клиентов).

~~Записи не знают ни языковой пары, ни тематики, поэтому термин из RU→DE
юридического проекта лез в промпт RU→EN медицинского.~~ Сделано: у записей есть
`lang`/`domain`, `_get_context` отдаёт только область проекта (`_project_scope`),
TM подбирается по своей языковой паре. Владельца (организацию) это не заменяет.

### 🟡 Нет журнала действий — 2-3 дня
Кто перевёл, кто подтвердил, кто одобрил термин — не сохраняется. Медицинский и
юридический перевод продаются вместе с ответственностью; первый же корпоративный
клиент спросит про аудит.

## 2. Масштабирование

### 🔴 Всё состояние — один файл в памяти процесса — 10-15 дней
`state.json`, ровно один воркер uvicorn, глобальный `STATE`
([CLAUDE.md, инвариант 1](CLAUDE.md)). Сейчас 6.8 МБ на один проект в 2670 сегментов.

Потолки, в которые упрёмся:
- второй воркер запустить нельзя — данные затрут друг друга;
- каждое сохранение переписывает файл целиком;
- десять клиентов по 3000 сегментов — это сотни мегабайт в памяти и секунды на запись;
- рестарт сервиса теряет очередь фоновых прогонов.

Нужна нормальная БД (PostgreSQL): проекты, сегменты, глоссарий, TM, очередь задач.
Это самая объёмная работа в списке и самая неизбежная.

### 🟡 `/api/seed` отдаёт 5.4 МБ при каждом входе — 1-2 дня
Все проекты вместе со всеми сегментами. На входе в систему браузер разбирает
пятимегабайтный JSON. Нужна ленивая загрузка: список проектов со счётчиками,
сегменты — только для открытого.

### ⚪ Экспорт PDF не реализован — 1-2 дня
DOCX и XLSX собираются по-настоящему, PDF в интерфейсе есть, но не работает.
~~Экспорт не сохраняет оформление исходника~~ — сделано: `docx_layout`
подменяет текст в самом исходном файле, шрифты, картинки и разметка остаются.

## 3. Языки

### 🔴 Поиск терминов заточен под русский оригинал — 5-7 дней
Стеминг ищет кириллические окончания: `[а-яёА-ЯЁ]*` ([main.py:164](backend/main.py#L164)),
ключи индекса — `[а-яёa-z0-9]+`, нормализация «ё→е». Для немецкого, французского,
узбекского оригинала морфология не сработает: глоссарий будет находить только
точные совпадения, то есть почти ничего.

Нужен подключаемый морфологический слой по языку (правила окончаний или готовый
стеммер), иначе продавать перевод «с любого языка» нечестно.

### 🟡 Маркеры отрицания есть только для RU и EN — 1 день на язык
`NEGATION_MARKERS` ([medical_qa.py:136](backend/medical_qa.py#L136)). Для других языков
проверка молча выключается — это честно, но проверки нет.

### 🟡 Правила направлений описаны только для RU→EN — 1 день на пару
`DOMAIN_RULES` теперь ключуется по (область, язык, язык), но заполнена одна пара.

### ⚪ Список языков и флагов зашит в интерфейсе — 0.5 дня
Пять языков в `langOpts` ([tab_import.jsx:54](frontend/js/tab_import.jsx#L54)) и
`FLAGS` ([ui.jsx:246](frontend/js/ui.jsx#L246)); в таблице сегментов флаги 🇷🇺/🇬🇧
проставлены прямо в заголовках столбцов.

## 4. Предметные области

### 🟡 Каталог областей правится только в коде — 2-3 дня
`DOMAINS` в [main.py:343](backend/main.py#L343): семь областей, промпты и категории
терминов внутри. Заказчик со своей спецификой (патенты, нефтегаз, страхование)
ждёт релиза вместо того, чтобы описать область сам. Нужен редактор областей
в интерфейсе: название, промпт переводчика, промпт проверки, категории.

### 🟡 Область проекта нельзя сменить после создания — 0.5 дня
Выбирается только при импорте; у старых проектов поля нет и они считаются
медицинскими.

### ⚪ Название «Medical QA» и медицинская лексика в интерфейсе — 0.5 дня
Карточка переименована в «Детерминированные проверки», но в коде остались
`medical_qa_enabled`, `risk_score`, `MEDICAL_QA_ENABLED`, тексты подсказок.

## 5. Данные и содержание

### 🟡 Эталонный глоссарий вшит в репозиторий — 2 дня
10 022 записи из `med_translation/assets/glossary/approved_glossary_FINAL.tsv`
поднимаются как стартовые данные для любой установки. Клиенту-юристу приезжает
медицинский словарь, а внутри — мусор вроде «Полноты → Fullnesses».
Нужны: пустой старт, импорт TSV/TBX и разметка «чей это словарь».

### 🟡 Демо-данные в коде — 0.5 дня
`SEED_PROJECTS`, `SEED_TEAM` («Анна Иванова», «Эпикриз — кардиология»)
([main.py:1025](backend/main.py#L1025)). При потере состояния сервис поднимается
с чужими выдуманными проектами — на демонстрации у клиента это выглядит плохо.

### ⚪ Импорт только DOCX — 3-5 дней
Ни PDF, ни XLSX, ни PPTX, ни XLIFF. Отраслевой стандарт обмена — XLIFF; без него
сервис не встроить в чужой процесс.

## 6. Коммерческие риски

### 🔴 Бесплатный Google-переводчик как запасной движок — 1-2 дня
`deep_translator` ходит в бесплатный веб-эндпоинт Google
([main.py:107](backend/main.py#L107)). Для платного сервиса это нарушение условий
использования и внезапный отказ при блокировке. Нужен официальный API с ключом
(он уже поддержан) и явный отказ вместо тихой подмены.

### 🟡 Учёт расхода есть, разреза по клиенту и лимитов нет — 2-3 дня
~~Фактический расход токенов нигде не сохраняется.~~ Сделано: `_note_usage`
снимает `usage` с каждого ответа модели, `_usage_end` кладёт итог прогона
в `STATE["runCosts"]` (последние `RUN_COST_HISTORY` записей) рядом со сметой,
которую видел человек, `/api/usage` отдаёт факт и поправку к смете.
Осталось для продажи: разрез по организации (упирается в мультиарендность),
лимиты с отказом при превышении и хранение в БД вместо `state.json`.

### 🟡 Цены моделей зашиты в коде — 1 день
`OPENAI_MODELS` с ценами, сверенными вручную 15.08.2026
([main.py:402](backend/main.py#L402)). Провайдер поменяет прайс — сметы начнут врать
до следующего релиза.

### 🟡 Один провайдер — 3-5 дней
Только OpenAI. Клиент с требованием «данные не покидают ЕС» или со своим
Azure/Anthropic-контрактом не обслуживается. Слой провайдеров абстрагируется
за 3-5 дней, промпты уже отвязаны.

### ⚪ Медицинские данные без явного контура защиты — оценка после юриста
Персональные данные пациентов уезжают в OpenAI. Для продажи медицинским
учреждениям нужен ответ про 152-ФЗ / GDPR / BAA: как минимум опция локальной
модели и договор с провайдером.

## Порядок, если продавать

1. **Мультиарендность + БД** — без этого второго клиента подключить нельзя (15-20 д).
2. **Разрез расхода по клиенту и лимиты** — сам расход уже пишется, но без
   разреза и потолка продажа за деньги остаётся лотереей (2-3 д).
3. **Официальный Google API вместо бесплатного** — правовой риск (1-2 д).
4. **Глоссарии по организациям + чистый старт** — иначе словари клиентов перемешаются (5 д).
5. **Морфология по языкам** — открывает пары кроме RU→EN (5-7 д).
6. **Редактор предметных областей** — снимает зависимость клиента от релизов (2-3 д).

Первые три — блокирующие: до них сервис продаётся ровно одному заказчику,
которому вы доверяете ключ от общей базы.
